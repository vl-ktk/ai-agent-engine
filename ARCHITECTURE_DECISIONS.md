# AI Agent Engine — архитектура и согласованные решения

**Зафиксировано:** 2026-11-16 (Europe/Kyiv)  
**Статус:** выбран собственный open-source агент и оркестратор на приватном VPS с SIWC/ChatGPT Plus; OAuth, серверный запуск и новый MCP ещё не проверены.  
**Назначение:** зафиксировать согласованную логику именно AI Agent Engine. Исходник этого проекта — `vl-ktk/ai-agent-engine` (`main`). Другие проекты и репозитории не используются для дальнейшей разработки этого движка. Это не журнал задач.

## 1. Цель

Единая облачная среда для работы GPT, Claude и других разрешённых исполнителей над несколькими независимо подключаемыми проектами, без необходимости держать домашний ПК включённым. Исходники, тесты, сборки, очередь задач и история работы доступны на сервере; подключение чужого проекта и публикация — только по разрешению владельца.

## 2. Выбранное направление архитектуры

- **Облачный VPS:** предварительный кандидат Hetzner CX33 (4 shared vCPU, 8 ГБ RAM, 80 ГБ NVMe, без GPU). Исторический ориентир обсуждения от 2026-11-16: €8,49/мес. + €0,50/мес. за IPv4 без НДС/дополнительных услуг; актуальную цену проверить перед покупкой. Сервер **не заказан**.
- **ChatGPT ↔ MCP ↔ VPS:** собственный защищённый MCP с узкими инструментами для чтения/записи файлов, выполнения тестов и сборок, получения логов, работы с версиями; критические действия требуют подтверждения.
- **Центральный оркестратор на VPS:** постоянная очередь, исполнитель задач, состояния, блокировки параллельной записи, журнал действий, память/контекст, передача задачи и проверка результата.
- **GPT и Claude:** равноправные исполнители. Конкретного исполнителя и границы задач определяет владелец. У Claude должен быть отдельно настроенный доступ; наличие MCP в ChatGPT не подключает Claude автоматически.
- **Исходники:** источник истины каждого проекта задаётся владельцем; VPS работает с согласованными копиями. Существующие сайты/Workers Cloudflare продолжают размещаться отдельно, не переносятся автоматически на VPS.
- **Codex и Claude Code:** необязательные инструменты/исполнители. Собственный runner может обеспечить операции с файлами и терминалом без обязательного использования этих приложений.

## 3. Фактическое состояние нового движка (2026-11-16)

1. Публичный GitHub-репозиторий `vl-ktk/ai-agent-engine` создан с MIT-лицензией; в `main` находится офлайн Python-прототип.
2. Подтверждён демонстрационный цикл в 3 шага и 10/10 unit-тестов (2026-11-16); тестовая модель — `ScriptedModel`, не GPT/Claude.
3. Работа других MCP в отдельных проектах не доказывает способность нового движка вызывать MCP, использовать OAuth или управлять VPS. Здесь эти интеграции **ещё не реализованы и не проверены**.

## 4. Поведение оркестратора

1. Получить поручение владельца и контекст проекта.
2. Проверить источник актуальной версии и разрешения.
3. Зафиксировать задачи, исполнителя, зависимости и состояние (queued / running / blocked / review / done / failed).
4. Позволить параллельную работу только в независимых частях; не допустить двух одновременно пишущих исполнителей в одном компоненте без решения владельца.
5. Выполнить необходимые безопасные инструменты, собрать тесты и логи.
6. Передать следующему исполнителю исходники, изменения, ограничения, результат проверок и короткий HANDOFF при необходимости.
7. Перед выпуском проверить текущую опубликованную версию повторно; при конфликте переосновать изменения и снова протестировать.
8. Запрашивать разрешение на production, расходы, секреты, права, опасные удаления и реальные внешние действия; сохранить ID версии для отката.
9. Сохранить критические решения и итоговую приёмку, не превращая GitHub в рутинный журнал.

**Два уровня:** детерминированный системный оркестратор (очередь/права/состояния) может работать без AI-запросов. Автономные планирование, анализ и написание кода требуют отдельно подключённой модели и лимитов.

## 5. Подписки и ограничения

- В обычном чате используется существующая подписка ChatGPT Plus. MCP даёт модели инструменты при обращении из чата; сам по себе MCP **не запускает непрерывно думающую AI-модель** на VPS.
- Вариант Sign in with ChatGPT (SIWC) для **открытого ПО на self-hosted VM** документирован OpenAI и потенциально позволяет авторизовать допустимые серверные AI-запросы через план Plus. **У нас эта авторизация ещё не настроена и не проверена.**
- Соответствие нашей частной системы условиям SIWC необходимо подтвердить отдельно: для закрытых облачных приложений может требоваться одобрение OpenAI. Не считать подписку безлимитной или автоматически заменяющей API.
- Не смешивать этот CPU VPS с отдельными проектами по выбору локальных моделей на GPU. При необходимости дополнительный вычислительный сервер подключается отдельным решением владельца; текущая архитектура от него не зависит.
- Безопасность: HTTPS/OAuth или защищённый туннель, разграничение по проектам, минимальные полномочия, аудит, резервные копии. Не публиковать произвольный незащищённый shell-доступ и не хранить токены в Git.

## 6. Что ещё не сделано

- Не арендован и не настроен VPS; нет серверного оркестратора и очереди.
- Не создан MCP самого AI Agent Engine для файлов, запуска тестов/сборки и DevOps.
- Не подключены исходники конкретных проектов к server runner.
- Не проверены SIWC/OAuth, фактические серверные AI-запросы через Plus, квоты и одобрение для нашего случая.
- Не настроен отдельный доступ Claude.
- Не создана собственная панель/виртуальное рабочее пространство.
- Ни одна production-версия или защита существующих проектов не изменялась в рамках этой фиксации.

## 7. Последовательность следующей реализации

1. Минимальный open-source прототип агента уже создан, опубликован и проверен офлайн. Далее — отдельно провести локальный OAuth через SIWC и завершить тестовый GPT-запрос по плану Plus **до оплаты VPS**. Локальный тест не заменяет последующую проверку на VPS.
2. По разрешению владельца подготовить VPS, защиту, доступы и резервные копии.
3. Реализовать минимальный системный оркестратор: очередь, состояния, audit, sandbox одного тестового проекта.
4. Подключить новый MCP к ChatGPT; проверить безопасное создание, чтение, изменение и удаление тестового файла, затем запуск тестовой команды.
5. Проверить модельный доступ и лимиты: SIWC/Plus (при соответствии условиям) или отдельно согласованный вариант.
6. Подключить Claude, затем реальные проекты по одному.
7. Добавить полноценные сценарии агентной работы и интерфейс управления.

## 8. Новое решение владельца от 2026-11-16: open-source + Plus без отдельного API-биллинга

**Утверждено как целевая архитектура:**
- Разработать **собственного, настоящего open-source ИИ-агента и оркестратор**, а не полагаться на обязательный сторонний агент. Публикуется работающий код той агентской системы, которая использует SIWC; не считать публичную пустую обёртку достаточной.
- В будущем разместить **личный экземпляр** системы на защищённом **приватном VPS** (Hetzner — кандидат), без предоставления платного или общедоступного облачного сервиса другим пользователям.
- Для GPT в автономном серверном режиме использовать **официальный Sign in with ChatGPT (SIWC) и личный ChatGPT Plus**. Не подключать обычный платный OpenAI API-ключ или отдельный API-биллинг без нового решения владельца. Технически SIWC использует разрешённые OpenAI endpoints с OAuth-токеном; это не обходит правила и лимиты OpenAI.
- **Публичен исходный код агента/оркестратора; приватны** экземпляр сервера, секреты, OAuth-токены, базы задач, память, переписки, конфигурации и исходники отдельно подключаемых рабочих проектов.
- GPT и Claude остаются равноправными исполнителями, назначение задач — только владельцем. Для Claude потребуется отдельная настройка доступа.
- **До аренды сервера** создать минимальный тестовый прототип и провести реальную OAuth-авторизацию SIWC под аккаунтом владельца, проверить разрешённые scopes, доступную модель, завершение одного запроса и реакцию на лимиты. Не утверждать, что доступ получен, пока тест не пройден.
- После аренды отдельно подтвердить **работу на self-hosted VM** и безопасное хранение/обновление токенов; успешный локальный тест сам по себе не подтверждает удалённый запуск.
- **Граница применимости:** OpenAI документирует OSS-клиент и самостоятельный запуск OSS на удалённой VM. Для закрытых облачных приложений, предоставляемых как сервис, указан отдельный доступ. Не утверждать, что связка из публичной обёртки и преимущественно закрытого облачного приложения гарантированно подпадает под OSS-сценарий.
- **Уже сделано:** публичный MIT-репозиторий и минимальный офлайн прототип, проверенный демо и 10 тестами. **Не сделано:** OAuth, реальное подключение моделей, VPS, новый MCP, production. Другие проекты не изменялись.

## 10. Решение владельца от 2026-11-16: иерархия оркестраторов и накопление опыта

**Утверждено как целевой дизайн; не реализовано и не развернуто:**

1. **Один общий системный оркестратор (программная часть)** для всего сервера: очередь, зависимости, состояния, блокировки, права, журнал, лимиты повторов и разрешения. Он управляет работой без обязательного вызова ИИ на каждый шаг.
2. **Один главный ИИ-оркестратор** для координации нескольких проектов, анализа комплексных задач, составления планов, диагностики сложных ошибок и обзора общего состояния. Его решения исполняет только системный оркестратор в пределах разрешённых правил.
3. **Оркестраторы отдельных проектов — гибриды «программа + ИИ», как главный**, но с ограниченным контекстом, журналом, знаниями, исходниками и задачами конкретного отдельно разрешённого проекта. Это логические роли внутри единой платформы: не требуются отдельная VM, модель или постоянно работающий ИИ-процесс на каждый проект. Программная составляющая может использовать общий системный оркестратор; проектная ИИ-роль вызывается по необходимости.
4. **Оркестраторы отделов/специализаций** (дизайн, backend, QA, безопасность) — *опциональны*, не создаются по умолчанию. Добавлять только при доказанной пользе для параллельных задач и согласовании с владельцем.
5. **ИИ-агенты-исполнители** получают задания и права согласно решениям владельца. GPT, Claude, Claude Code и Codex равноправны: никакого постоянного закрепления frontend/backend за конкретной моделью. Один исполнитель не забирает чужую текущую задачу без указания владельца.
6. **Цикл ошибки:** исполнитель/тестер записывает воспроизводимый дефект → системный оркестратор фиксирует статус и журнал → при необходимости ИИ-оркестратор анализирует причины и варианты → задача возвращается назначенному ответственному исполнителю (смена исполнителя — только по решению владельца) → тесты повторяются. Ограничить число автоматических повторов; эскалация владельцу при зацикливании или неопределённости.
7. **Самообучение в первой версии означает улучшение рабочих процессов, а не обучение весов GPT/Claude:** отдельные уровни памяти (общие правила, проект, агент, проверенные решения), воспроизведение успешных подходов, автоматические регрессионные тесты, объективные оценки качества, предложения по улучшению инструкций и маршрутизации. Не превращать непроверенные гипотезы в постоянные правила. Применение изменений к глобальным правилам или правам — после оценки и одобрения владельца; история изменений и откат обязательны. Обучение собственных весов/LoRA — отдельная будущая инициатива, не часть MVP.
8. **Контроль владельца:** видимость дерева задач и ответственных, приоритетов, результатов и изменений; возможность остановить задачу или сменить исполнителя. Production, расходы, изменение секретов/прав, опасное удаление и внешние действия — только по явному разрешению владельца.
9. **Конфиденциальность:** рабочие репозитории, память, журналы, токены и конфигурации закрыты; публичен только согласованный open-source код агентной платформы. Межпроектное переиспользование — лишь проверенные технические практики без секретов и чужих данных.

**Единый план разработки:** [IMPLEMENTATION_ROADMAP.md](./IMPLEMENTATION_ROADMAP.md). Пункты на верхнем уровне предварительные; детали и критерии приёмки разбирать с владельцем по одному этапу. Планирование не является подтверждением успешной OAuth-авторизации, наличия VPS или работы агентов.


## 11. Решение владельца от 2026-11-16: живое визуальное пространство агентов

**Обязательное требование к будущей панели, реализацию и дизайн отложить до этапа 9 плана.**

- Пользователь ранее показывал видео-референс **виртуального города/карты**, где ИИ-агенты представлены персонажами, перемещаются и наглядно выполняют действия. Нравится объединение **организации мультиагентной системы** с такой **живой визуализацией**.
- Предусмотреть **одно большое общее расширяемое пространство** для всех проектов, агентов и ролей; при добавлении нового агента/проекта пространство не должно требовать переписывания архитектуры.
- Движение, активности и взаимодействия на экране должны быть **связаны с реальным состоянием** задач, переходами, работой, ожиданием, ошибками, проверками и результатами — не просто декоративная анимация.
- Пользователь должен иметь возможность наблюдать за агентами, выбрать агента, увидеть его текущую задачу и статус, общаться с ним и выдавать разрешённые задания (через единую систему полномочий).
- Не фиксировать пока визуальный стиль, размещение «районов», способ движения, 2D/3D, движок и UX деталей. Принцип, дизайн, макеты и реализацию обсуждать **только при переходе к этапу 9**; не разрабатывать эти элементы сейчас.

**Статус:** требование согласовано, реализации и визуальных макетов ещё нет. Это не новый двенадцатый этап, а часть этапа 9 «MCP и панель владельца».
