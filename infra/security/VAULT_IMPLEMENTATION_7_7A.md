## Реализовано в исходниках

- `ai_agent_engine/secure_vault.py`: отдельная private SQLite (каталог `0700`,
  файл `0600`) с application ID, schema version, `foreign_keys`, синхронной
  записью и без незашифрованных значений секретов в таблицах.
- Библиотека `cryptography` объявлена зависимостью пакета. Отдельный
  Vault-установщик проверил её на Netcup **до** создания ключей; старый
  контроллер не заменялся.
- AES-256-GCM с независимым случайным nonce для каждой версии и AAD,
  связывающим owner/project/secret ID/версию/тип; ключ передаётся только
  доверенным внешним `key_provider`, не генерируется и не записывается в
  SQLite/исходник. Проверки неверного ключа и подмены ciphertext.
- Динамические категории, стабильные ID, перемещение/переименование,
  обратимое архивирование; идемпотентная область проекта по команде
  доверенного владельца.
- Save/Get/Update/List/Grant/Revoke, отдельный разрешённый Save в категории
  для исполнителя, общие секреты между проектами **без копирования**,
  ограничение по actor/project/operation/expiry и немедленный отзыв grant.
- Метаданные и аудит действий без содержимого секретов. SQL-триггеры
  запрещают штатное `UPDATE`/`DELETE` audit; это **не** внешний неизменяемый
  журнал и не защита при полном захвате владельца SQLite.
- `VaultOrchestratorBridge`: доверенный in-process вызов сохранения секрета
  владельца без второго подтверждения и использование в рамках действующего
  разрешения с возвратом только `bool`, не пароля. Это интерфейс для будущего аутентифицированного чата,
  **не** готовый ChatGPT/MCP/HTTP-коннектор.
- `vault_runtime.py`: отдельный системный пользователь `ae-vault`, локальный
  UNIX-сокет `ae-vault.socket`, проверка UID Linux через `SO_PEERCRED`,
  шифрованные systemd credentials и отдельный приватный SQLite. Режим
  работы без Windows-ПК; никакого открытого порта/API для паролей.
- Локальный зашифрованный snapshot с проверкой изолированного восстановления
  и ежедневным systemd timer. По решению владельца **всё на Netcup**;
  полная потеря VPS уничтожит и резервные копии — это не off-host DR.
- `vault_client.py`: **исходный код** доверенного серверного клиента для
  `ae-runtime` и интерфейс `VaultOrchestratorTasks`. Проверяет UID владельца
  UNIX-сокета и UID обслуживающего процесса, не доверяет `is_owner` из
  сообщения; Save/Get/Update/List не логируют значения. `ae-runtime` может
  сохранять только в категории с заранее выданным Vault grant. Этот
  клиент включён в интерфейс `MainOrchestratorVault` в исходниках
  `main_orchestrator.py`, но не в действующий процесс контроллера.

## Нерешённые границы до приёмки

1. **Живой главный оркестратор**: текущий `main_orchestrator.py` —
   библиотека, установленный системный контроллер — heartbeat, а не
   обработчик owner-сообщений. Важно включить `MainOrchestratorVault` в
   реальный работающий процесс **после** запуска самого оркестратора.
   Подключение этого отдельного ChatGPT-чата и новый MCP не требуются.
2. **Доверенный вход владельца в главный оркестратор**: он должен
   аутентифицировать владельца до обработки сообщения и передавать
   значение как байты в `MainOrchestratorVault`; не давать модели
   выдавать себе `is_owner`, гранты или доступ к чужим проектам.
3. **Однократная выдача scoped разрешений `ae-runtime`** после наличия
   проверенной идентичности owner-chat и связанного проекта; отзыв и
   раздельные реальные runtime-идентичности GPT/Claude/Codex.
4. Полная live E2E проверка Save/Get/Update/Revoke на синтетических
   значениях из настоящего обработчика, ресурсы, прерывание/восстановление
   и поддерживаемая процедура ротации. Нет необходимости отправлять в тесты
   настоящие пароли или менять уже действующие учётные данные.

**Правила для тестов:** только синтетические секреты и временные приватные
папки. Не переносить существующие credential files и не создавать здесь
настоящие пароли, ключи, `.env` или owner recovery secret.
