# AI Agent Engine — Secure Vault (P1, этап 7.7A)

**Решение владельца: 20.11.2026. Статус: `[ ]` ЗАПЛАНИРОВАНО, НЕ РЕАЛИЗОВАНО.**

Самостоятельный инфраструктурный модуль после архитектуры 7.7 и до
масштабирования автоматического создания новых проектов. Номер `7.7A` сохраняет
существующие 169 прямых подпунктов и не меняет смысл 7.7/7.8. Пять фаз ниже —
внутренние контрольные этапы **одного** нового элемента плана, а не новые
трёхуровневые номера. Никаких новых прав или разрешения на production-релиз
эта запись не даёт.

## 1. Назначение и границы

Создать на существующем Netcup VPS круглосуточно доступный централизованный
Secure Vault, независимый от включения Windows-ПК. Он обслуживает разрешённые
компоненты AI Agent Engine и исполнителей GPT, Claude, Codex и будущие
**утверждённые** роли. Хранить логины, пароли, SSH-ключи и серверные доступы,
API-ключи и токены, OAuth access/refresh tokens, учётные данные БД,
служебные ключи и другие секреты. Все записи принадлежат одному владельцу и
имеют явную область использования; разрешённость модели не равна доступу ко
всем секретам.

Не смешивать Vault с существующим этапом 4.17:
`/etc/ai-agent-engine/secrets` — созданный ранее **пустой** каталог с
root/групповыми правами и **без шифрования значений на диске**. Он не является
готовым Secure Vault. Миграция, заполнение, изменение прав, токенов или
архитектуры доступа требуют отдельного review/разрешения.

## 2. Динамическая структура

Начальные категории-примеры, не жёсткая схема:

1. **Servers:** Netcup, Oracle, новые VPS и хосты.
2. **Services:** Cloudflare, GitHub и другие платформы.
3. **AI:** API-ключи разрешённых AI-платформ.
4. **Projects:** AI Agent Engine, KTK Social, ATHL, новые проекты.
5. **Accounts:** логины, пароли, OAuth-сессии.
6. **System:** БД, конфигурации, служебные ключи.

- Произвольное количество логических категорий, вложенных разделов, серверов,
  сервисов, аккаунтов и проектов; защита квотами/лимитами ресурсов без
  фиксированного перечня категорий в коде.
- Создание, переименование, перенос, архивирование и восстановление структуры
  через доверенный API без остановки Vault и пересборки кода.
- Каждому разделу и секрету назначать стабильный внутренний ID. Перенос и
  переименование не меняют ссылку потребителя и не прерывают подключение.
- При одобренном создании проекта — идемпотентно создать его область и
  назначить только предварительно разрешённые роли/права.
- Один секрет может использоваться в нескольких проектах по отдельным
  ссылкам и независимым scoped-разрешениям, без копирования значения.
- Удаление с явным подтверждением владельца: сначала обратимая архивация с
  tombstone, проверка зависимых подключений и срока хранения; окончательное
  необратимое уничтожение — отдельное разрешение и проверка резервных копий.
  Отзыв прав действует сразу, даже если запись ещё восстановима.

## 3. Управление и API

Доверенный сервис и главный оркестратор реализуют проверяемые операции:

| Операция | Обязательная семантика |
| --- | --- |
| **Save Secret** | Защищённый ввод/генерация, проверка владельца, scope, запись ciphertext и метаданных, возврат только идентификатора |
| **Get Secret** | Разрешённое использование через broker/credential injection; сырое значение не передавать в контекст LLM или API-ответ по умолчанию |
| **Update Secret** | Атомарная версия, проверка зависимостей, безопасная ротация и откат |
| **Revoke Secret** | Немедленный отзыв доступа/сессии внутри системы; внешнюю ротацию только с полномочиями владельца |
| **List Secrets** | Только доступные ID, типы и безопасные метаданные без plaintext/токенов |
| **Manage Vault** | Управление разделами, ACL, общими ссылками, архивом и журналом с owner-approval для опасных операций |

Главный оркестратор вправе **организовывать** утверждённые задачи сохранения и
использования секретов, но не выдавать себе новые права. Сценарий «Сохрани
данные Oracle-1»: владелец выбирает защищённый канал ввода, ядро проверяет
решение и сохраняет данные, оркестратор сообщает ID/статус **без значения**.
Созданные исполнителем ключи автоматически попадают в соответствующую область
**только** через заранее разрешённую операцию и защищённый канал; при
отсутствии grant — HOLD/вопрос владельцу, без plaintext в логах.

Права: owner → project → actor/service identity → конкретная запись → операция
→ срок/контекст; deny-by-default, TTL, немедленный revoke, аудит отказов,
невозможность межпроектного чтения, запрет наследовать чужие гранты.
Возможность делиться одним значением не снимает запрет на его передачу
неодобренному исполнителю.

## 4. Передача учётных данных владельцем

- Владелец может сознательно передать данные главному оркестратору. Сам факт
  отправки в приватный чат **не означает автоматическую обязательную** смену
  пароля. При признаках компрометации предупредить и предложить ротацию.
- Однако обычный AI-чат **не является гарантированно защищённым каналом
  ввода**: содержимое может остаться в истории/системах провайдера. Основной
  режим — отдельный защищённый ввод, минующий контекст и журналы LLM.
- Значения не повторять в ответах, GitHub, исходниках, документации,
  `HANDOFF.md`, трейсах, stdout/stderr, промптах или отчётах.
- При сознательной передаче через чат не обещать технического удаления из
  истории провайдера; предупреждать о реальном риске без навязывания ротации.
- Пароли сторонних сервисов, секреты других проектов и права доступа менять
  только в пределах действующего подтверждённого решения владельца.

## 5. Безопасность и восстановление

1. Аутентифицированное шифрование каждой версии секрета на диске;
   шифрование metadata/backups там, где метаданные раскрывают доступы.
2. Раздельное управление ключами шифрования; ключ расшифровки не хранить
   рядом с ciphertext в доступной тому же процессу открытой форме.
3. Защита от подмены/повтора записи, компрометации одной роли и доступа
   другого проекта; точные независимые ACL на actor/project/operation.
4. Секреты не возвращать модели: scoped broker выдаёт только минимальную
   возможность подключения или временный дескриптор целевому процессу.
5. Аудит append-only действий (кто/когда/какая операция/результат/ID/версия),
   без значений, headers, passwords, ключей и OAuth payload.
6. Отдельные **зашифрованные off-host** резервные копии, retention, защищённый
   экспорт и проверенное изолированное восстановление без перезаписи production.
7. Аварийный recovery material — только у владельца **вне Netcup**;
   задокументировать утрату ключа/сервера и порядок безопасной ротации.
8. Защита от несанкционированного чтения, записи, удаления и повышения прав;
   тестировать symlink/traversal, replay, concurrency, revocation race,
   injections, журналы и ошибочные ответы.
9. Отдельная угроза: шифрование на диске **не защищает** от захвата процесса,
   который уже имеет право расшифровывать. Требуется изолировать broker,
   ключи, процессы и доступ исполнителей; выбрать реалистичную модель угроз.
10. Любое внешнее KMS/HSM, новое хранилище или платный ресурс — только после
    отдельного выбора и согласия владельца; здесь заказов и расходов нет.

## 6. Пять фаз реализации — все `[ ]`

- [ ] **Фаза 1 — Vault Storage.** Модель записей/стабильных ID и дерева,
  encryption-at-rest, envelope/key lifecycle, scoped ACL и безопасное хранение.
  **Проверка:** ciphertext на диске; чужой scope не получает plaintext; restart,
  corruption/rollback и ключевой отказ не приводят к раскрытию.
- [ ] **Фаза 2 — Vault API.** Save/Get/Update/Revoke/List/Manage, перемещения
  без разрыва ссылок, версии, общий секрет без дублирования, audit/owner
  confirmation. **Проверка:** отрицательные RBAC/TTL/revoke/cross-project,
  concurrency и журнал без значений.
- [ ] **Фаза 3 — Orchestrator Integration.** Защищённый ввод без попадания в
  LLM, автоматическая постановка допустимых задач, credential broker и
  разрешённое использование GPT/Claude/Codex. **Проверка:** end-to-end
  synthetic secret без plaintext в prompts/API logs/GitHub; отсутствие grant
  даёт HOLD, не новый grant.
- [ ] **Фаза 4 — Project Automation.** Автосоздание области нового
  owner-approved проекта, ACL, добавление серверов/сервисов, динамические
  категории, независимые общие ссылки. **Проверка:** повторная постановка
  идемпотентна, перенос не ломает потребителя, чужие проекты изолированы.
- [ ] **Фаза 5 — Security & Recovery.** Threat-model, adversarial tests,
  backup/restore/recovery key, нет утечек и проверка ресурсов/отката.
  **Проверка:** зашифрованная off-host копия восстановлена в изоляции;
  ревокация и восстановление тестируются без потери рабочих данных.

## 7. Общая приёмка Secure Vault

Модуль можно отметить `[x]` **только** после доказательств всех десяти пунктов:

1. Секреты сохраняются, читаются через разрешённый broker и обновляются.
2. На диске и в сервисных временных файлах нет plaintext-копий.
3. Исполнители получают только точные разрешённые операции/доступы.
4. Оркестратор автоматически организует сохранение и использование с
   реальным owner/grant gate, без самовыдачи прав.
5. Утверждённые новые проекты получают области и наименьшие ACL автоматически.
6. Структура меняется без правки кода, остановки сервиса или разрыва ссылок.
7. Общие секреты используются из одной записи без дублирования значений.
8. Логи, GitHub, ответы, prompts, отчёты не раскрывают значений.
9. Зашифрованная резервная копия реально восстановлена в тестовом контуре
   с owner-held recovery material.
10. Offline/CI и разрешённые live security, restore и E2E проверки успешны.
