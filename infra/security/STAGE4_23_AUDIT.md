## Netcup: живые read-only проверки

- `ss -ltn`: только **`0.0.0.0:22`** в состоянии `LISTEN` на момент проверки. Это снимок TCP-слушателей в гостевой ОС, не внешний port scan.
- Эффективное `sshd -T`: `permitrootlogin no`, `passwordauthentication no`, `kbdinteractiveauthentication no`, `pubkeyauthentication yes`.
- `systemctl is-active ssh.service ae-controller.service ae-backup.timer ae-host-check.timer`: **все четыре `active`**.
- Netcup SCP → Firewall: **`Firewall active` включён**; применяется пользовательская политика **AI Agent Engine VPS - SSH and NTP ingress** (входящий SSH TCP/22, входящий UDP-ответ NTP с source 123), а также стандартные правила Netcup SMTP block (исходящие 25/465/587) и разрешения ping IPv4/IPv6. Последними неявными правилами являются **drop all incoming** / **accept all outgoing**. Не меняли порядок и правила.

Успешные последующие backup-пробы есть в журнале. Выполнен **только** `systemctl reset-failed 'run-p*'` (сброс статусов временных units), `systemctl --failed --no-pager` после → **`0 loaded units listed`**. Журнал не очищали, действующие units не меняли, причину самостоятельного раннего отказа штатной `ae-backup.service` из 4.18 по этому факту **не устанавливаем**.

## Итог, границы и возможные решения

**Подпункт 4.23 выполнен в согласованной области:** проверены админ-политики GitHub, доступы и безопасность действующего VPS; по разрешению владельца установлены базовая защита `main`, allowlist GitHub Actions и обязательный SHA-pin, выполнено подтверждённое безопасное устранение исторических FAILED-флагов временных тестов. GitHub CI до изменения политики — SUCCESS; после сохранения политики отдельный owner-manual workflow не запускали, его жизненный сценарий не заявляем проверенным.

1. **Сохраняемый компромисс:** ruleset запрещает deletion/force-push, но **не обязывает PR или status checks для прямой записи в `main`**. Это осознанно сохраняет текущую owner fast-forward публикацию, не равнозначно полной защите от ошибочного обычного коммита. Ужесточение порядка публикации — отдельное решение владельца.
2. **GitHub Actions:** все 14 используемых `uses` закреплены на полных SHA в исходниках, административная политика тоже требует полный SHA. [CI #44294405496](https://github.com/vl-ktk/ai-agent-engine/actions/runs/44294405496), [VPS automation config #44294405379](https://github.com/vl-ktk/ai-agent-engine/actions/runs/44294405379), [CI #44297978945](https://github.com/vl-ktk/ai-agent-engine/actions/runs/44297978945) — SUCCESS. Последний имел 5 warnings об устаревшем Node.js 20 в pinned `actions/setup-python` (GitHub принудительно выполняет на Node 24); это **не падение CI**, обновлять pinned refs без отдельной проверки не стали.
3. **Незакрытые наблюдения:** первоначальная ошибка штатной backup-службы 4.18 остаётся необъяснённой; нет off-host копии, полной проверенной восстановимости при потере VPS/диска также нет. Эти риски не маскировать фактом `systemctl --failed = 0`.

**Не проверялось:** внешний скан всего адресного диапазона/IPv6, pentest, каждый Marketplace Action, полноценное owner-manual workflow после новых разрешений, восстановление с независимого устройства, полное удаление VPS. Нет оснований объявлять «сервер полностью безопасен».

**Версии и откат:** GitHub `main` до завершения исправлений документации — `511e284e6fb42b7d5d89d18f526d7b97a317d954` (до первых шагов 4.23 — `d95fccaeed0df3e69578b771416f08f903f5f6a7`). Отмена документации — только адресным обратным коммитом поверх актуального `main`, без force push. GitHub settings не откатываются `git revert`, их возможный возврат требует отдельных admin-действий и оценки риска. Контроллерный релиз `85375103800845eeff696e53f510c66c428408ed` не менялся, серверный rollback не требуется. Следующий пункт плана — **4.24**, только по отдельной команде владельца.
