# WEB-15 — private queue, cold-start reconciliation (21.11.2026)

**OFFLINE MOCK ONLY, Linux/SQLite.** `ai_agent_engine/chatgpt_web_recovery.py`, opt-in `WebRecoveryCoordinator` поверх WEB-12 task core, WEB-13 durable delivery и WEB-14 bound fault guard; `tests/test_chatgpt_web_web15.py`. Внешнего ChatGPT browser driver/долговечной browser login-сессии всё ещё **нет**.

## Источники истины и структура

- **TaskInbox** private SQLite schema v17 остаётся канонической задачей: owner/project, prompt, assigned worker, `TaskState`, permissions/approvals. Не копировать task prompt в новый журнал. Netcup рабочая SQLite v14 не меняется.
- **WEB-13** private SQLite journal schema1 и существующий `TaskDeliveryManager` удостоверяют issued attempt, lease, response digest и ACK; активный/неопределённый delivery никогда не повторяют автоматически.
- **WEB-15** отдельный private SQLite `AWRC` schema1 хранит `agents(owner,project,agent,chat_project,profile,mailbox,fault_code)` и FIFO `queue(task_id,scope,checkpoint_id,revision,checkpoint_sha,request_sha,state,ordinal,time)`. Только metadata и SHA-256, ни prompts, ни instructions, ни memory bodies, ни cookie/token/password/ответов. Каталог `0700`, БД `0600`, `O_NOFOLLOW`, exclusive `flock`, `synchronous=FULL`, integrity+foreign-key check. Новые task DB миграции не нужны; максимум **128** незавершённых очередных указателей (настраивается 1..128).

## От регистрации до перезапуска

1. Только trusted `WebRecoveryCoordinator.enqueue` проверяет существующие TaskInbox/approved specialist pin, exact WEB-12 request, owner/project/agent/profile/mailbox, свежую membership WEB-04, `ScopedCheckpointSnapshot` из проверенного injected WEB-11 source: `current/verified`, `revision`, `checkpoint_sha256(status,summary,next_action)` и `status=in_progress`. Пауза/блокировка checkpoint не разрешает send. FIFO пишет **только ссылку на задачу** `PENDING` до browser.
2. При штатном явном `dispatch_next` сначала выполняется `inventory` и сверка с обоими WEB-13 журналами, затем атомарный `PENDING→IN_FLIGHT` **до** вызова `WebIdempotentDispatcher`. Успех при проверенном `SUCCEEDED` и durable ACK → `COMPLETED`. Только доказанное capacity denial до браузера (`retryable` + journal `DEFERRED`) → `PENDING` и bounded backoff (`WAIT` до срока). Нет background runner, таймера, автологина, silent retry или переключения модели.
3. После холодного рестарта trusted caller **снова** создаёт registry/agent/profile/WEB-08 policies, bind protected `GuardedBrowserPort` к тому же логическому owner/project/agent; `inventory()` заново проверяет membership, checkpoint и хеш заново реконструированного request из TaskInbox. Только исходный `PENDING` с отсутствующим delivery или proven `DEFERRED` может стать `READY` для явного ручного вызова. Никогда не восстанавливается сырой chat transcript или действующая cookies/login-сессия.
4. Любой `IN_FLIGHT` после аварии, неизвестная/несогласованная запись, изменённый checkpoint/профиль, `RUNNING` с `ACTIVE` delivery, `SUCCEEDED` без ACK → durable task `HOLD` и durable fault агента `UNKNOWN_SEND`, без второго вызова BrowserPort. После рестарта `WebFaultGuard` снова получает sticky HOLD. Fault callback, установленный ровно один раз в guard, записывает известный WEB-14 `WebFaultCode` в SQLite **до** подтверждения локального HOLD. Неизвестность не разрешается по одному истечению lease.
5. Нормально завершённый task с `TaskState.SUCCEEDED` + `TaskDeliveryManager.completed` + WEB-13 `ACKED` при recovery подтверждается как `COMPLETED`, в том числе если crash случился после ACK, но до записи в WEB-15 очередь. Разрыв между отдельными базами **не** является общей транзакцией — неопределённый исход всегда HOLD. Без отдельного решения владельца не делаем опасного `HOLD→READY`.

## Что проверено и что не обещаем

16 Linux unit: сохранённая, но ещё не отправленная задача успешно исполняется после пересоздания registry/SQLite; штатный ACK восстанавливается; стоп после crash в `IN_FLIGHT`; настоящий `os._exit(37)` дочернего процесса **внутри** mock BrowserPort, повторное открытие трёх SQLite и отсутствие второго send; rate-limit/CAPTCHA fault persisted; concurrent double-resume→1 BrowserPort, FIFO/metadata checks, `0600/0700/flock`, чужая БД, foreign keys, SHA pin change, paused checkpoint, capacity deferred→safe resume, bounded queue, запрет `HOLD→PENDING`. Это проверка локальных фиктивных компонентов, не живого ChatGPT.

**Ограничения:** нет фактического сохранения/возобновления настоящего ChatGPT UI conversation, browser cookies, real project membership или live модели; порты создаются заново из доверенной локальной конфигурации, их live login не восстанавливается. Нет автоматически разблокируемой ручной сверки неизвестного внешнего результата: такой task останется HOLD до отдельного протокола и полномочия владельца. Не доказаны subscriber quotas, `TECH_GO`, `POLICY_GO`, `INTEGRATION_GO`, server rollout. WEB-16 — следующая полная offline-приёмка multi-agent/multi-project; только затем отдельная разрешённая оценка реального доступа.
