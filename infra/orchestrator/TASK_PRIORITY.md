# 5.4 — приоритеты и выбор следующей задачи AI Agent Engine

**Область:** локальный прототип системного оркестратора на `127.0.0.1`.
Без запуска моделей, назначений исполнителей, новых серверов и расходов.

## Правило выбора

1. В пределах **одного проекта и владельца** исключаются задачи,
   которые уже помечены завершёнными **доверенным внутренним кодом**.
2. Из остальных рассматриваются только задачи, **все зависимости
   которых завершены**. Сам по себе родитель `parent_task_id`
   зависимостью не считается (5.3).
3. Из доступных задач выбирается **максимальный приоритет**.
4. При одинаковом приоритете — **раньше принятая задача** (`receipt`).
   Если нужна дополнительная гарантия полного порядка, используется ID.

Приоритет — **целое число 0–100**, большее число означает выше приоритет.
По умолчанию `0`. `bool`, дробные числа, строки и значения за пределами
диапазона отвергаются. Изменение приоритета **не меняет ID задачи**,
её владельца, родителя, зависимости или исходный текст.

Например: задача A с приоритетом 100 зависит от B с приоритетом 0.
Пока B не завершена, A **не может** быть выбрана. Если рядом есть
независимая задача C с приоритетом 50, выбирается C; после подтверждённого
завершения B система сможет выбрать A.

## Локальный HTTP-контракт

- `POST /v1/tasks`: необязательное поле `"priority": 0..100`;
  если его нет, приоритет `0`. В ответе `202` присутствует `priority`.
- `PUT /v1/tasks/{task_id}/priority` с **ровно** одним JSON-полем
  `{"priority": 90}` — атомарное изменение приоритета существующей задачи.
- `GET /v1/tasks/{task_id}` содержит текущий `priority`, но **не**
  возвращает постановку задачи.
- `GET /v1/projects/{project_id}/next-task` — безопасный предварительный
  выбор задачи **без отметки выполнения**. Ответ:
  `200 {"status":"selected","project_id":"project-a","task_id":"...","priority":90}`
  либо `200 {"status":"no_ready_task","project_id":"project-a","task_id":null}`.
- Выбор следующей после завершения предпосылок доступен **только
  доверенному Python-коду**:
  `TaskInbox.select_next(project_id, scope, completed_task_ids=(...))`.
  HTTP-клиент **не может** передать поддельные завершения через query/body.

| Отказ | Код |
| --- | --- |
| Отсутствующая/чужая задача при `PUT` | `404 not_found` |
| Некорректный `priority`, лишние поля, неверный тип | `422 invalid_priority` |
| Некорректный JSON/повторяющийся JSON-ключ | `400 invalid_json` |
| Чужой проект в `GET /next-task` | `403 project_forbidden` |

Для `PUT` применяются лимиты тела, `Content-Length` и `Content-Type`
из [контракта API](./TASK_INTAKE.md). Права — только доверенный
`OwnerScope` 5.2, чужие задачи/проекты не видны.

## Границы этапа

Это **чистый выбор кандидата**, не резервирование и не выполнение.
С 5.6 уже закреплённые за worker+workspace задачи исключаются из выбора;
повторное назначение такой задачи запрещено. [Назначения](./TASK_ASSIGNMENT.md).
Повторный `GET /next-task` может вернуть ту же задачу, потому что пока
**нет машины состояний и подтверждений завершения** (этапы 5.7–5.8).
Нет попыток угадать завершение по наличию `receipt`, HTTP-ответу `202`
или по тексту задачи. Выбор по доверенно переданным completed ID подготавливает
интерфейс для будущей машины состояний, но не принимает их от сетевого
клиента. Защита от двойного назначения — 5.6.

Без `--db` приоритеты, DAG и задачи **только в RAM**. При `--db` в 5.5
они сохраняются в [приватной SQLite](./TASK_DURABILITY.md) и переживают
перезапуск процесса.
HTTP всё ещё без аутентификации клиента; **не открывать публично**.
В 5.4 не менялись Netcup, production-БД, секреты, systemd и порты.

**Приёмка:** `python3 -m unittest tests.test_task_priority -v`, полный
`unittest discover`, compileall, source/workflow checks; локальные HTTP
тесты без обращения к платным API.
