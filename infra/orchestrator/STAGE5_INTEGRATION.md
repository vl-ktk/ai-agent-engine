# Пункт 5.14 — интеграционная offline-проверка ядра этапа 5

Дата: 18.11.2026. Только **AI Agent Engine** (`vl-ktk/ai-agent-engine`).
Никаких моделей, внешних сервисов, запросов к LLM, расходов или Netcup.

## Контракт восстановления

В `TaskDeliveryManager.recovery_inventory(trusted_scope)` добавлен
**полный, scoped, read-only перечень всех незавершённых задач**.
Каждая запись содержит только `task_id`, `state`, `delivery_status`
(`None`, `active`, `retryable`, `exhausted` и т. д.) и `review_required`.
Промпт, worker ID, workspace-путь, токен доставки, пароль и аргументы
операций в этот перечень не попадают.

- `QUEUED` без delivery → `review_required=False`: задача ожидает обычного
  назначения. Сам метод ничего не запускает и не назначает.
- `ASSIGNED` или `RUNNING` **с любым статусом**, включая **отсутствующую
  запись доставки**, → `review_required=True`: требуются проверка
  состояния предыдущего исполнителя и безопасное решение доверенного
  оператора. Никакого автоматического повторного запуска.
- После **любого** падения SQLite при перечислении метод отказывает
  целиком (`StorageUnavailable`), не выдавая неполный перечень за полный.
- Терминальные `SUCCEEDED`, `FAILED`, `CANCELLED`, `TIMED_OUT` не являются
  зависшими незавершёнными задачами и в инвентарь не включаются.
- Применяется существующая SQLite **v5**, новый сервер/БД/миграция не
  нужны. `resume_pending()` сохраняет прежний контракт delivery-only;
  для общей диагностики использовать именно `recovery_inventory()`.

## Проверки

Команда:

```bash
python3 -m unittest discover -s tests -p test_stage5_integration.py -v
```

13 независимых offline-сценариев:

1. Восемь реальных параллельных изолированных Python-процессов на восьми
   workspace: выдача, RUNNING, завершение, ACK, restart, ноль незавершённых.
2. Шестнадцать конкурирующих claim одного workspace: победитель ровно один,
   другие учтены как QUEUED; освобождение и повторное занятие workspace.
3. Реальные два запуска одной задачи при failure/retry, новый durable token
   только после остановки предыдущего; один workspace и успешный restart.
4. Отмена Linux-группы вместе с дочерним процессом, освобождение lease.
5. Таймаут долгого процесса одновременно с успешным другим процессом.
6. Имитированный отказ SQLite **после** остановки процесса: RUNNING
   остаётся в инвентаре и lease не теряется; повторная фиксация завершения.
7. RUNNING без delivery row: старый `resume_pending` пуст,
   новый `recovery_inventory` явно показывает опасную неопределённость.
8. Scoped-инвентарь QUEUED/ASSIGNED/RUNNING и запрет выдачи повторного
   активного токена; чужой владелец не получает данные.
9. SQL-отказ при инвентаризации не маскируется частичным списком.
10. Durable authorization audit после restart; незаявленное опасное
    действие не совершает побочного эффекта.
11. Копия **закрытой тестовой** SQLite: `integrity_check`, восстановление
    task state, журнала и delivery без незавершённых задач.
12. Реальный HTTP на `127.0.0.1`: idempotent POST → claim → durable ticket
    → отдельный Popen → отказ/разрешение gate → cancel → restart → аудит.
13. **Реальный аварийный `SIGKILL` отдельного supervisor:** дочерний
    процесс остаётся жив (это наблюдалось), `RUNNING/active` сохраняется,
    inventory требует проверки, повторный token не выдаётся, workspace
    держится. **Только тестовый доверенный reconciler** затем завершает
    зафиксированную группу, проверяет отсутствие живых членов, записывает
    failure и терминальное состояние; после restart инвентарь пуст.

## Границы и безопасное восстановление

**Важно:** после неуправляемого `SIGKILL` управляющего процесса дочерний
Linux-процесс **может продолжить работу**. Ядро этапа 5 пока не умеет
автоматически проверить его PID/время запуска и безопасно убить после
нового старта. Выдавать такую зачистку за PASS запрещено. Требование 5.14
«никаких *неучтённых* зависших задач» относится к **полноте долговечного
учёта**; не означает, что процесс гарантированно уничтожен любым крашем.
Автоматическое управление реальным исполнителем без оставшихся процессов
входит в следующий этап, в том числе **6.9**.

После незапланированного рестарта доверенный оператор обязан:

1. Поднять приватную task SQLite и восстановить workspace lease;
   при SQLite/lease ошибке остановить операции (fail closed).
2. Выполнить `recovery_inventory` для доступных ему owner/project scopes;
   отдельно разобрать **каждую** запись с `review_required=True`.
3. Проверить результат в среде исполнителя и все его дочерние процессы;
   **не** считать `RUNNING` остановленным на основании одного рестарта.
4. До нового запуска убедиться, что старый исполнитель не работает и что
   внешнее действие не было уже выполнено. Если доказательств нет, не
   переисполнять неизвестный active ticket.
5. Только после проверки выполнить разрешённый терминальный переход/ACK
   либо отдельно утверждённый retry; затем повторить inventory и убедиться,
   что все ожидающие ручной разбор записи объяснены.

Это локальный тестовый контур доверенного Python-кода. Ни запуск реальных
GPT/Claude, ни production-откат, ни тест аварийного восстановления VPS,
ни гарантии exactly-once внешних эффектов здесь не выполнялись.
