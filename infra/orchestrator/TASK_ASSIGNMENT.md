# 5.6 — атомарное назначение исполнителя и каталога AI Agent Engine

**Результат:** у задачи может быть **ровно одна неизменяемая пара**
`worker_id + workspace_dir`. Оба значения закрепляются под одним lock и
в одной транзакции SQLite (если включён `--db`). При одновременных
попытках только один претендент получает `201 assigned`, все остальные
получают `409 already_assigned`; уже назначенная задача больше не
выбирается через `GET /next-task`.

## Доверенный корень рабочих каталогов

- При запуске локального сервера указывается дополнительный
  `--workspace-root /ПУТЬ_К_ПРИВАТНЫМ_КАТАЛОГАМ`.
- Этот корень **уже существует**, принадлежит пользователю процесса и
  имеет права `0700`. Внутри существуют заранее подготовленные каталоги
  вида `slot-one`, каждый также `0700` и того же владельца.
- HTTP-клиент передаёт **только имя одного дочернего каталога**
  (`workspace_name`), а не произвольный абсолютный путь.
  `..`, `/`, симлинки, несуществующие каталоги и открытые права запрещены.
- `WorkspaceRoot` проверяет корень и дочерний каталог через `lstat`.
  **Никаких каталогов при назначении не создаёт, не меняет и не удаляет.**
- Реальный абсолютный `workspace_dir` вычисляется из доверенного корня
  и записывается вместе с `worker_id`.

Локальная проверка без внешней сети, после того как администратор
самостоятельно подготовил приватные каталоги:

```bash
python3 -m ai_agent_engine.task_api \
  --port 8765 \
  --owner-id owner-a --project-id project-a \
  --db /ПУТЬ_К_ПРИВАТНОЙ_БД/inbox.sqlite3 \
  --workspace-root /ПУТЬ_К_ПРИВАТНЫМ_КАТАЛОГАМ
```

## HTTP-контракт

После получения ID задачи через обычный `POST /v1/tasks`:

```http
POST /v1/tasks/{task_id}/claim
Content-Type: application/json

{"worker_id":"worker-a","workspace_name":"slot-one"}
```

Успешный `201 assigned` содержит `task_id`, `worker_id`,
`workspace_name` и проверенный абсолютный `workspace_dir`.
`GET /v1/tasks/{task_id}/claim` возвращает те же метаданные (`200`)
или `404 not_found` для неназначенной, неизвестной или чужой задачи.

| Ответ | Причина |
| --- | --- |
| `201 assigned` | Закреплена первая пара worker+workspace |
| `409 already_assigned` | Пара уже закреплена, даже если её запросил тот же worker |
| `422 invalid_assignment` | Отсутствуют/неверны поля `worker_id`, `workspace_name` |
| `422 invalid_workspace` | Нет доверенного корня/каталога или приватных прав |
| `404 not_found` | Чужая/неизвестная целевая задача |
| `503 storage_unavailable` | SQLite не подтвердила атомарную запись |

Действуют те же ограничения `Content-Length`, размера, JSON/UTF-8 и
безопасных ответов, что в [API](./TASK_INTAKE.md). Запрос с `owner_id`
отвергается: доверенный владелец по-прежнему назначается сервером.

## Долговечность и проверки

- В собственной SQLite AI Agent Engine **v2** появилась таблица
  `task_claims`, где `task_id` — primary key. Переход **v1 → v2**
  создаёт только новую таблицу в транзакции, не переписывает задачи/DAG.
- Если `--db` указан, HTTP подтверждает назначение **после commit**.
  После перезапуска worker+workspace восстановятся и повторное назначение
  той же задачи останется запрещено. Без `--db` назначение временно.
- Проверены 32 конкурирующие операции из разных потоков, 16 одновременных
  HTTP-запросов, миграция v1, повторный запуск настоящего HTTP-процесса,
  права/симлинки/подмена путей, чужие владельцы/проекты и отказ SQLite.
- Защита от двойного назначения действует **внутри одного TaskInbox**;
  второй процесс с той же SQLite блокируется одиночным `flock` из 5.5.

## Границы пункта

1. **Назначение — только запись метаданных**, не запуск GPT/Claude,
   не создание рабочей директории и не выдача реальных ОС-прав.
2. На момент 5.6 разные задачи **могли ссылаться на один каталог**.
   Начиная с **5.9**, одна активная задача удерживает OS-level
   [блокировку каталога](./WORKSPACE_LOCKS.md); следующая получит
   `409 workspace_busy`. После терминального состояния каталог
   освобождается без изменения исходной записи назначения.
3. Нет освобождения назначения/lease/таймаута или переходов состояния:
   машина состояний — **5.7–5.8**, отмена и timeout — **5.11**.
4. Нет аутентификации локального HTTP-клиента. Любой, кто получил доступ
   к loopback-порту, может заявить произвольный `worker_id` в пределах
   доверенного owner scope. **Не открывать наружу** до авторизации.
5. На рабочем Netcup сервере никакой каталог, БД, systemd, порт или
   секрет не менялись. Новые VPS/платные услуги не требуются.

Код: `ai_agent_engine/task_assignment.py`, `TaskInbox.claim_task`,
`SQLiteTaskStore.task_claims`. Приёмка:
`python3 -m unittest tests.test_task_assignment -v` и полный regression.
