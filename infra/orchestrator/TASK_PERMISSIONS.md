# 5.13 — гранты на опасные действия и обезличенный аудит

**Область:** только AI Agent Engine, приватная task SQLite и доверенный
локальный контроллер. Это не изменение реальных прав пользователей,
секретов, аккаунтов, Netcup или других проектов.

## Принцип: запрет по умолчанию

- Новый `TaskPermissionGate(inbox, grants=...)` принимает список **строго
  типизированных `ActionGrant` из доверенной конфигурации процесса**.
  Каждый грант закрепляет **один `task_id`, одного назначенного worker и
  одно действие**. Не поддерживаются wildcard, публичные HTTP-grants,
  автоматическая выдача прав по тексту задачи или саморазрешение модели.
- Фиксированный `ProtectedAction`: `read_secret`, `write_workspace`,
  `execute_tool`, `external_request`, `delete_artifact`. Это **категории
  разрешений**, а не команды/URI/пути; сама по себе проверка не выполняет
  оболочку shell, сетевой запрос или файловую операцию.
- `TaskPermissionGate.run(task_id, trusted_owner_scope, actor_id,
  action, trusted_callback)` сверяет область владельца/проекта,
  неизменное назначение worker, текущее состояние **`RUNNING`**, точный
  грант и его срок. Если любого условия нет, возвращает `PermissionDenied`
  без запуска callback. Неизвестное/чужое задание отказывается до аудита,
  без раскрытия существования записи.
- Разрешение **не означает успешное выполнение действия**: журнал пишет
  только проверку прав, и только после commit разрешения запускается
  переданный доверенным кодом callback. Исключение из callback не
  трактуется как успешный результат инструмента.
- `TaskProcessController(..., permission_gate=gate).execute_protected(...)`
  добавляет реальную границу для локально запущенного управляемого
  процесса. Контроллер проверяет, что процесс жив, задача работает и
  deadline не истёк, и удерживает **локальный per-task lock** во время
  проверки/вызова; параллельные независимые задачи не блокируются.
  При отсутствии gate **защищённое действие не выполняется**.

## Долговечный обезличенный журнал

- Та же приватная task SQLite расширена **v4→v5** одной транзакцией,
  без отдельной БД и без копирования. Для прежних собственных v1–v4
  миграция сохраняет задачи, состояния, назначение и retry ledger.
- `task_permission_audit`: монотонный `event_id`, непрозрачный `task_id`,
  **только категория** действия, `allowed` (0/1), ограниченный
  `reason_code`, `principal_kind` (`assigned_worker/other_worker`) и UTC.
  Нет имён/ID пользователей или worker, prompt, title, ключей, путей,
  параметров инструмента, результатов операции или внешних токенов.
- Причины: `granted`, `grant_missing`, `grant_expired`,
  `worker_mismatch`, `task_not_running`.
- И разрешение, и отказ должны быть **закоммичены до** ответа/вызова.
  При ошибке SQLite (в том числе отказ trigger) callback **не запускается**.
  Журнал читается только через доверенный `audit_history(task_id,scope)`;
  чужой scope получает отказ. Публичного HTTP API журнала нет.
- Сами гранты **не сохраняются** в БД: при рестарте их должен снова
  предоставить доверенный конфиг процесса, иначе доступ снова запрещён.
  Никакой новый ключ/пароль/системное разрешение не создаётся.

## Проверено

`python3 -m unittest discover -s tests -p test_task_permissions.py -v`

24 отдельные проверки: запрет опасной записи/удаления **до побочного
эффекта**, отказ + событие SQLite, точные/чужие/просроченные гранты,
worker/owner isolation, отсутствие полей с секретами, 32 конкурентных
запрета и 32 журнальных события, сохранение аудита после SQLite restart,
SQL trigger/storage failure → fail-closed, безопасная миграция v4→v5,
недоступный HTTP endpoint, два независимых исполнителя без глобальной
рабочей блокировки. **Три теста с реальными изолированными `Popen`**
проверяют связь с `TaskProcessController`: без grant и без gate опасное
действие не запускается; с точным grant разрешённая операция проходит,
а другая отклоняется и журналируется.

## Честные границы

1. Это **внутренний authorization gate для доверенного исполнения**, не
   полноценный внешний login/OAuth и не замена ОС-песочницы. HTTP-приём
   всё ещё только `127.0.0.1` и не имеет установленной пользовательской
   аутентификации. Не открывать его наружу, не принимать grants из JSON.
2. Все потенциально опасные **будущие адаптеры** должны проходить через
   gate. Прямой Python-вызов произвольного стороннего кода вне этого
   контракта не может быть им остановлен; протокол требует доверенного
   исполнения. Права файловой системы/сети не менялись.
3. Решение пишется до callback; при гонках/длительных операциях и
   аварийном завершении действует принцип fail-closed. Нагрузочные,
   аварийные, restart/restore интеграционные проверки без LLM — 5.14.
4. Никаких production-изменений Netcup, его controller/database,
   systemd, портов, секретов, платных сервисов и других проектов.
