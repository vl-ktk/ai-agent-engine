# 6.6 — файловые операции только внутри назначенного task workspace

**Статус:** файловые инструменты локального ядра защищены от выхода за
границу заранее созданной рабочей области; задача из SQLite теперь может
использовать эти инструменты **только через доверенный `TaskWorkspaceFiles`**
и явные гранты. Это **не** sandbox всего Linux-процесса, браузера или
модели: OS-изоляция отдельная задача **6.8**, shell/Git — **6.7**.

## Реализовано

- В `ai_agent_engine/tools.py` существующий `SandboxFiles` использует
  POSIX `openat`/`dir_fd` и `O_NOFOLLOW` для каждого сегмента пути.
  При создании экземпляра запоминает `(st_dev, st_ino)` доверенного
  корневого каталога; при каждой операции сверяет inode открытого root FD.
  Это закрывает замену исходной директории другой папкой/симлинком между
  проверкой строки и открытием файла. Отдельно запрещены traversal `..`,
  абсолютные пути, Windows-style, NUL, `:` и пустые компоненты.
- **Чтение:** только существующего регулярного файла, `st_nlink == 1`,
  до заданного лимита и в строгом UTF-8. Никаких FIFO, устройств, hardlink,
  симлинков (в том числе последнего сегмента) или файлов за пределами
  рабочего каталога. Не читаем чужие секреты вне workspace.
- **Запись:** только **нового** UTF-8 файла с `O_CREAT|O_EXCL`, `0600`,
  заданным лимитом содержимого. Нельзя перезаписать существующий файл,
  создать произвольную папку, удалить, переименовать или следовать
  пользовательской ссылке. Сбой кодировки безопасно отклоняется.
- Новый `ai_agent_engine/task_workspace_files.py`: `TaskWorkspaceFiles`
  принимает доверенные `TaskInbox` (SQLite), `OwnerScope`, `task_id`,
  `worker_id` и **тот же** `TaskPermissionGate`; берёт `workspace_dir`
  только из зафиксированного `TaskAssignment` (а не из аргумента модели).
  Перед действием снова сверяет назначение и проверяет текущий статус
  `RUNNING` через gate. На платформе без POSIX `dir_fd`/`O_NOFOLLOW`
  этот task-bound инструмент **недоступен** — небезопасного fallback нет.
- **Гранты:** чтение требует `EXECUTE_TOOL`, запись требует **оба**
  `EXECUTE_TOOL` и `WRITE_WORKSPACE`. Gate пишет обезличенное решение в
  приватную SQLite до I/O; отсутствие любого гранта = отказ без действия.
  Role/описание действия в JSON не превращается в право.

## Подключение из доверенного координатора

```python
from ai_agent_engine.task_workspace_files import TaskWorkspaceFiles

# Trusted `inbox`, `scope`, `task_id`, `worker_id`, `gate`; задача уже
# закреплена за существующим приватным каталогом (0700).
files = TaskWorkspaceFiles(
    inbox, scope, task_id=task_id, worker_id=worker_id, gate=gate,
)
file_tools = files.allowed_tools()  # read_file, write_new_file
```

Нельзя передать `owner_id`, `workspace_dir`, `worker_id`, другой `task_id`
или shell-команду через `read_file`/`write_new_file`. Обе операции
принимают только `path` (и для записи `content`). Пространство доступа
сохраняет назначение, даже если задача или каталог изменились.

Действующие **GPT 6.2** и **Claude 6.3** пока вызываются как
одноразовые модели **без файловых инструментов**. Эта реализация
подготавливает безопасное подключение file tools в дальнейшем;
не утверждать, что Claude/GPT уже получили файловые операции в live.

## Реальные негативные тесты

`tests/test_task_workspace_files.py` выполняет изолированные Linux
операции только в `TemporaryDirectory`: допустимая запись/чтение;
другой workspace; абсолютные пути и `../`; директории и файлы через
симлинк; hardlink внешнего файла; FIFO; одновременная замена внутренней
папки на symlink и замена root на другой inode; ошибки кодировки;
недействующий worker, чужой owner; отсутствие одного/двух грантов;
попытки доступа до состояния `RUNNING`; модель через существующий
`Agent`/`Tool` без API и сетевого соединения. Внешние тестовые файлы
проверяются на неизменность.

```bash
python3 -m unittest tests.test_task_workspace_files -v
python3 -m unittest discover -s tests -q
python3 -m compileall -q ai_agent_engine tests
python3 scripts/check_workflow_boundaries.py
python3 scripts/check_public_source.py
```

**Границы:** это защита **конкретных файловых API**, а не гарантия,
что произвольный исполняемый бинарник с правами того же Linux UID не
прочитает иной путь. Модельный процесс сам по себе не получает права
вызывать эти API за пределами доверенного координатора. Требования к
shell/Git — 6.7, к жёсткой OS/secret изоляции — 6.8, к безопасной
передаче и реальной проверке SHA артефактов — 6.12. Никаких новых
разрешений модели, внешних API, изменений Netcup/production/секретов.
