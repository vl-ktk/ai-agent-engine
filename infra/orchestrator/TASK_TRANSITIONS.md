# 5.8 — проверка переходов и журнал попыток AI Agent Engine

**Граница:** только **AI Agent Engine** и его отдельная приватная SQLite
очередь (`ai_agent_engine/task_storage.py`). Работающий Netcup controller и
его основная БД (`ai_agent_engine/task_db.py`) не изменяются.

## Что работает

- Внутренний, доверенный `TaskInbox.transition_state(task_id, target,
  trusted_scope, actor_id=...)` проверяет все рёбра `TaskState` из
  [схемы 5.7](./TASK_STATES.md). Его **нет в HTTP API**.
- `queued → assigned` выполняется **только** через атомарный
  `TaskInbox.claim_task`: отдельный вызов изменения статуса отклоняется
  как `claim_required`, не создавая фиктивного worker/workspace.
- Разрешённые переходы фиксируются **в одной транзакции** с событием
  `accepted=true`. Неразрешённые, повторные и терминальные переходы
  не меняют статус, но фиксируются `accepted=false` с кодом отказа.
- Для запуска `assigned → running` и результатов
  `running → succeeded/failed` требуется совпадение `actor_id` с
  закреплённым в 5.6 `worker_id`. Отказ — `worker_mismatch`. Это
  **локальная логическая проверка**, не полноценная аутентификация:
  доверие к вызвавшему коду задаёт сервер. Права и гранты — этап 5.13.
- `queued → cancelled` и иные рёбра схемы могут выставляться только
  **внутренним вызовом**. Они изменяют запись задачи, но **не запускают
  и не останавливают ОС-процесс**; контролируемая отмена/таймаут
  выполнения реализуются отдельно в 5.11.
- `GET /v1/tasks/{id}/state` теперь читает реально сохранённый статус,
  включая `running`/терминальный, если его **явно записал доверенный код**.
  `PUT/POST .../state` не поддерживаются. Неизвестные/чужие задачи
  по-прежнему не раскрываются.
- Планировщик не выбирает отменённые/завершённые задачи; подтверждённые
  `succeeded` могут разблокировать зависимые задачи DAG.

## Приватная SQLite v3 и миграция

- Собственная task DB v3 (`application_id = 0x4145494E`) содержит
  `task_states` с одним состоянием на `task_id` и
  `task_transition_audit` с монотонным `event_id`, `task_id`,
  `from_state`, `to_state`, `actor_id`, `accepted`, `reason_code`,
  `occurred_at` в UTC.
- Не пишутся prompts, имена задач, пути рабочих каталогов и секреты.
  HTTP-`worker_id` при claim пока **заявленный идентификатор**, а не
  подтверждённая личность. Журнал доступен через доверенный
  `TaskInbox.transition_history(task_id, trusted_scope)`, не HTTP.
- Собственные v1/v2 мигрируют в v3 **одной явной транзакцией**;
  существующие tasks/DAG/claims не перезаписываются. Ранее назначенным
  задачам устанавливается `assigned`, неназначенным `queued`.
  Исторические события старых версий **не выдумываются**.
- Один приватный SQLite writer, `0700` каталог, `0600` файл,
  `synchronous=FULL` и блокировка `flock` сохранены. Состояние и
  аудит commit'ятся совместно до успешного ответа внутреннему коду.
- При ошибке SQLite операция возвращает `StorageUnavailable`, RAM и
  состояние на диске остаются прежними; **не считается успешной**.
- Режим без `--db` держит состояния и журнал **только в RAM**; после
  перезапуска их не восстановить.

## Зафиксированные причины отказа

| `reason_code` | Значение |
| --- | --- |
| `invalid_edge` | Переход отсутствует в графе, в т. ч. повтор или выход из терминального состояния |
| `claim_required` | Попытка назначить `assigned` минуя атомарное закрепление |
| `worker_mismatch` | Исполнитель не совпадает с назначенным worker |
| `already_assigned` | Повторный `claim` по уже закреплённой задаче |
| `not_queued` | Попытка `claim` после отмены/другого изменения статуса |

Проверки типа некорректных enum/ID отклоняются **до записи** журнала;
неизвестные и чужие ID не позволяют заполнить журнал чужой задачи.
Отказ записи самого аудита возвращает ошибку хранения, а не код
успешного/зафиксированного отказа.

## Проверки и ограничения

`python3 -m unittest tests.test_task_transitions -v`:

- все 7×7 пары рёбер сверены с канонической схемой;
- разрешённые переходы в разных ветках, отказ терминальным и повторам;
- 32 конкурирующие попытки запуска одной задачи: 1 успех, 31 отказ,
  плюс исходный claim — 33 события в журнале;
- миграция v2→v3, восстановление состояний/событий после SQLite restart;
- сбой транзакции аудита через SQL trigger: откат статуса и отсутствие
  ложного подтверждения;
- запрет прямого `assigned`, маскировка чужих задач,
  запрет HTTP-изменения состояния.

**Важно:** это проверенный **локальный механизм учёта состояний**, а
не реальный запуск/остановка AI-исполнителей. Подлинность внешних worker,
права на файловые операции, таймауты, retry и resume будут реализованы
в последующих пунктах. Никаких новых платных сервисов или серверов.
