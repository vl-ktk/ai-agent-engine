# 7.6 / вопрос №10 — проверяемое offline-ядро памяти (вариант В)

Утверждено Владиславом 20.11.2026. Канонический источник — GitHub
`vl-ktk/ai-agent-engine`, `main`. Этот код **не запущен на Netcup**,
не подключён к GPT/Claude и не создаёт платный сервис.

## Что реализовано

- `ProjectMemoryStore(ProjectLeaderStore)` использует только уже одобренные
  владельцем scope и проектное workspace 7.5. Файлы разных проектов —
  независимые `leader.sqlite3` в приватных owner/project каталогах.
  Изоляция наследует Linux `flock`, проверки POSIX mode/owner,
  `O_NOFOLLOW` и проверку существующей идентичности workspace из 7.5.
- При открытии созданной в 7.5 project SQLite происходит **атомарная
  миграция v1→v2**, без стирания `identity`/`management_refs` и без
  изменения реестра `project-leaders.sqlite3` и центральной task SQLite.
  Новая база сразу v2. Чужие и будущие `user_version` отклоняются.
- `memory_events`: append-only значимые `decision/plan/task/qa/error/
  checkpoint/lesson/source`, статус `proposed` или `verified`,
  `source_ref`, `source_sha256`, ревизия, idempotency key, ссылка
  `supersedes_id`. Конкурирующие замены одного события → HOLD;
  прежнее событие остаётся. Статуса `owner_approved` в API записи
  **нет**, поэтому текст модели не превращается в решение владельца.
- `memory_summaries`: краткие сводки с обязательными актуальными
  verified-event IDs, `expected_revision` (CAS), SHA-256 payload,
  журналом и историей. Старую ревизию можно запросить. Возврат к
  прежнему тексту создаёт **новую** ревизию с reason `restore:<n>`;
  удаление/переписывание прошлых событий и сводок не допускается.
- `events`: ограниченная literal-substring выборка SQLite со статусом,
  типом, provenance и лимитом результатов. По умолчанию старые
  superseded-факты не выдаются как актуальные; отдельно допускается
  запрос аудиторской истории `include_superseded=True`. Индекс по
  `(status,event_kind,created_at)`; поиск внутри своей проектной БД.
  Это **не FTS5** и не semantic ranking.
- `context`: JSON-конверт с маркером `UNTRUSTED_MEMORY_DATA_ONLY`,
  сводкой и релевантными текущими проверенными событиями, без
  произвольных SQL и грантов. Доверенный вызывающий слой обязан
  предоставить **реальный tokenizer целевой модели** и размер общего
  бюджета с резервом под задачу/ответ/инструменты; без этого — HOLD.
  Если уже сводка не вмещается, HOLD; иначе список событий уменьшается,
  не меняя долговременное хранилище.
- Базовая фильтрация очевидных секретов/секретных путей на входе,
  эвристический детектор явных prompt injections в модели контекста,
  ограниченный audit (`memory_audit`) с дедупликацией повторных HOLD.
  Проверенная QA-запись всё равно остаётся **данными**, не приказом.

## Программные границы доверия

`OwnerScope` и `verified` получает **только уже доверенный** сервисный
вызывающий код. Модели, специалисты и HTTP-клиенты **не должны** вызывать
`ProjectMemoryStore` напрямую или формировать доверенную область доступа,
отметку о проверенном источнике и счётчик токенов. Наличие SHA-256 само
по себе не означает, что исходный отчёт, коммит или владелец
аутентифицированы; это ответственность будущего отдельного ingestion
adapter и его gates. Проверка источника здесь структурная и scoped,
**не семантическая**: модель может предложить ошибочную фразу, но не
переписать историю, выдать grant или создать утверждение владельца.

Явные вредоносные инструкции, распознаваемые консервативной эвристикой,
вызывают `ProjectMemoryHold` + безопасный audit marker. Это не
доказательство обнаружения **всех** prompt injections или секретов:
отдельный действующий `TaskPermissionGate` обязательно контролирует
любые внешние эффекты в будущем live-пайплайне.

## Примеры интерфейса (доверенный offline вызывающий слой)

```python
memory = ProjectMemoryStore(leaders)  # leaders: approved ProjectLeaderStore
event = memory.append_event(
    owner_scope, project_id, event_kind="qa", body="Checks passed",
    source_ref="github:repo@exact_sha", source_sha256="a" * 64,
    status="verified", idempotency_key="qa-run-id",
)
summary = memory.propose_summary(
    owner_scope, project_id, expected_revision=0,
    body="A verified QA report exists.",
    event_ids=(event.event_id,), reason="qa",
)
prompt_data = memory.context(
    owner_scope, project_id, query="Checks", count_tokens=target_tokenizer,
    total_tokens=approved_total_budget, reserved_tokens=approved_reserve,
)
```

Числа и тестовые идентификаторы **не являются** утверждёнными рабочими
лимитами. Реальные бюджеты, способ обнаружения значимых событий,
верификация внешних источников и модельная интеграция подлежат
отдельной приёмке.

## Проверки и непокрытые возможности

`tests/test_project_memory.py` покрывает миграцию 7.5, рестарт,
неизменность старых ссылок, конкурентный CAS, idempotency,
supersession, двух владельцев/два проекта, отсутствие сквозной
выдачи контекста, попытку подделать scope, непроверенные факты,
SQL-wildcards, очевидные секреты и prompt injection/HOLD/audit,
точный тестовый счётчик бюджета. Полный регресс и сборка пакета
проводятся отдельно перед публикацией.

**OPEN / DEFERRED — только после отдельных замеров ресурсов и разрешения:**

- FTS5 и/или локальная semantic reranking/embeddings; измерить RAM,
  CPU и размер индекса для настоящего корпуса, согласовать квоты.
- Фоновая/пакетная индексация, наблюдение за отставанием и
  восстановление вторичного индекса. Сейчас единственная каноническая
  база обновляется непосредственно транзакцией; отдельного индекса нет.
- Общий owner-scoped каталог обезличенных QA-уроков для проектов:
  согласовать sanitization, реальную проверку источников и политику
  публикации, исключить утечки и дополнительную дисковую нагрузку.
- Продвинутые TTL/архив/backup project memory, автоматические события
  от модели, owner-auth UI и точные tokenizer/контекстные бюджеты.

**Windows, GitHub workflows, Netcup VPS, production, секреты и права не менялись.**
