# 6.11 — запрет конфликтующих изменений одной рабочей области

## Правило

**Один доверенный исполнитель и одна активная задача на один физический Linux workspace-каталог.** Уже существующий `WorkspaceRoot.acquire` закрепляет directory FD (`O_DIRECTORY|O_NOFOLLOW`), проверяет inode/владельца/`0700`, затем удерживает неблокирующий `flock(LOCK_EX|LOCK_NB)`. `TaskInbox.claim_task` атомарно фиксирует назначение или отказывает до открытия исполнительной сессии. Логический project_id сам по себе **не** является блокировкой: два разных проекта, назначенные в **одну** физическую папку, также конфликтуют.

Прямое сообщение для Python-исполнителя: `WorkspaceBusy: workspace already in use by another active task`. Публичный scoped HTTP-контракт остаётся совместимым: `409 {"status":"workspace_busy"}`. В `task_transition_audit` записывается обезличенная причина `workspace_busy`, без prompt, путей или данных другого владельца. Отказавшая задача остаётся `QUEUED`.

## Доказательство: два реальных процесса, не имитация mutex

`python3 -m unittest tests.test_task_workspace_edit_conflict -v`

1. GPT владеет `shared`, запускает реальный gated subprocess, записывает тестовый marker и остаётся `RUNNING`. Claude, назначенный для другого проекта, пытается ту же `shared` и получает `WorkspaceBusy`, без запуска процесса, без marker, delivery, permission/provider audit и без назначения. В SQLite сохранён `workspace_busy`.
2. Обратный порядок: Claude владеет `shared`, GPT отвергается тем же способом.
3. Для каждого порядка первая задача освобождает область только после успешного завершения. Вторая после этого исполняется точно один раз; вторичная выдача того же task не запускается. После повторного открытия частной SQLite обе задачи остаются `SUCCEEDED`, история отказа сохранена.

Проверки выполняют **настоящие локальные Linux child processes** через существующие `GPTTaskExecutor` и `ClaudeTaskExecutor` (gated launch + SQLite process ledger v8), но используют только детерминированный `python -u -c` ответчик. Никаких реальных LLM, подписочных запросов, платных API и фоновых задач.

## Фактические результаты CI и ограничения

PR #55: GitHub Actions Python 3.11/3.12/3.13 на Ubuntu PASS, сборка wheel PASS; Python 3.12: **590 unittest OK**, включая 2 новых теста. Windows/Python 3.12 продолжает FAIL на ранее существовавшем Linux-only `fcntl`, новый тест имеет platform skip guard.

`flock` не является межхостовым distributed lock. Гарантия относится к **одному каталогу** на локальной Linux filesystem и доверенному механизму выдачи задач; если исполнитель намеренно обходит инструменты или изменяет произвольные файлы через полноценный shell вне sandbox, такой код не становится безопасным от одной блокировки. Реальные сетевые GPT/Claude CLI пока не помещены в обязательный OS-sandbox (6.8). Не утверждать, что предотвращены конфликты Git на разных независимых каталогах или гарантированы права записи каждого процесса. Netcup и production не затронуты.
