# WEB-10 — автоматическая безопасная ротация mock-чата

**21.11.2026.** Десятая из двадцати внутренних задач текущего 7.11, исходный пакет `0.3.35a0`. Код: `ai_agent_engine/chatgpt_web_rotation.py`, расширение `ProjectChatManager.rotate_idempotent`/`restore_verified` и `tests/test_chatgpt_web_web10.py`.

## Что реализовано

1. `WebAutomaticChatRotator.rotate_on_pressure` читает **последний реально проверенный** WEB-09 `ContextPressureDecision` (`ROTATE`/`EMERGENCY`) и запускает переход **без повторной отправки** заблокированного запроса. `WARN`/`OK` и поддельные/устаревшие решения не инициируют новый чат. Триггер 75% и аварийные 90% — только заявленная консервативная эвристика, не достоверная web-квота.
2. Используется прежний WEB-04 membership gate и та же WEB-03 агентная FIFO. `ProjectChatManager.rotate_idempotent` требует точный прежний `conversation_id`, неизменные `agent_id`/`task_id`, и только injected mock `create_or_get_chat(chatgpt_project_id, predecessor_id, task_id, rotation_id)`. **Никакого fallback** к неидемпотентному `create_chat` при неопределённом исходе. В `ProjectChatRecord` фиксируются task/rotation ID и связь `predecessor↔next` внутри того же `chatgpt_project_id`.
3. `SQLiteWebRotationJournal` — опциональный локальный **тестовый** журнал (`PREPARED` → `COMMITTED`) с scope/operation/task/checkpoint CAS и атомарным пополнением истории чатов. `rotation_id` детерминирован по scope, `task_id`, `checkpoint_id` и предшественнику; уникальная задача не может получить противоречащую ротацию. `restore_agent` восстанавливает проверенную цепочку из SQLite в новый mock ChatManager; неверная история отклоняется. Это узкий журнал WEB-10, **не** production TaskInbox или замена будущей миграции SQLite/WEB-15.
4. После потери процесса между созданием mock-чата и записью результата повтор той же операции сначала подтверждается у **идемпотентного mock-порта**, затем коммитится единственный переход. Если локальный менеджер уже успел применить переход, а SQLite ещё нет, повтор также не создаёт второй чат. После `COMMITTED` дальнейшие повторы возвращают прежнюю квитанцию без вызова порта. Новый task/checkpoint или чужой scope → отказ.
5. `WebRotationReceipt` связывает прежний и новый chat с тем же owner/project/agent/task/checkpoint/rotation. Сама ротация **не выполняет задачу**, не подтверждает её результат и не повторяет BrowserPort. После успешного handoff следующий модельный запрос требует отдельного управления из TaskInbox/доставки (`WEB-12/13`).

## Что реально доказывают проверки

Тесты создают два разных mock проекта/агента, проходят путь `WEB-09 ROTATE → WEB-10 same-project create → lineage → explicit next turn`, проверяют 75%/90%, отказы по неверному project/member/proof/checkpoint/task и старый неидемпотентный port. Одновременные повторы сохраняют единственный `conversation_id`; есть fault injection в точках после remote mock create и до локального SQLite commit, восстановление fresh session/ChatManager/monitor/journal. Отдельный тест **завершает настоящий дочерний Python-процесс через `os._exit(37)` после создания mock-чата**, затем восстанавливает PREPARED из того же SQLite-файла и проверяет, что второго создания не было.

**Границы:** mock-сервис сам реализует устойчивое `create_or_get` по ключу — обычный ChatGPT UI такого официального контракта здесь не предоставлял. Поэтому это **только offline доказательство алгоритма**, а не гарантия отсутствия дублей при live браузерной автоматизации. Долговечный TaskInbox/lease/ACK, полноценный серверный restart и scoped-memory bootstrap относятся к WEB-11…15. Нет реального ChatGPT Web, обхода лимитов подписки, новых затрат, Netcup deployment или `POLICY_GO`.
