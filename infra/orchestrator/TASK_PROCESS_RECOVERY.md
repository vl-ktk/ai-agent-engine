# 6.9 — проверяемая остановка и восстановление исполнителя после crash

**Готово локально 18.11.2026.** Изменения: `task_process_identity.py`, `task_launch_gate.py`, `task_process_recovery.py`, `TaskProcessController`, `GPTTaskExecutor`, приватная task SQLite **schema v8**. Это внутренний доверенный workflow, а не HTTP-команда, сетевой API, готовый сервис на Netcup или автоматическое повторение запросов к моделям.

## Что устранено

В 5.14 реальный тест `SIGKILL` контроллера оставлял его дочерний процесс работающим без способа узнать PID после перезапуска. Теперь при управляемом запуске:

1. `TaskProcessController.launch_gated()` запускает в отдельной сессии маленький доверенный `task_launch_gate` — он ждёт один байт от контроллера. При EOF (авария до подтверждения) **вообще не выполняет** фактическую команду GPT/Claude.
2. Контроллер проверяет назначенного worker, отдельный `pid=pgid=sid`, private SQLite и сохраняет в `task_process_runs` версию процесса — `pid`, `pgid`, `sid`, Linux `/proc/[pid]/stat` **field 22 start_ticks**, текущий `/proc/sys/kernel/random/boot_id`, `worker_id`, `launch_kind`, `status`. `RUNNING` и аудит фиксируются только после этого; затем `G` разрешает фактический worker exec. Даже при crash на промежуточном шаге неизвестный worker не начинает работу без durable записи.
3. При штатном `finish`, `cancel`, timeout, завершении неудачной попытки и retry запись становится `stopped` **только после проверки остановки группы**, а terminal state/lease фиксируются по прежним правилам. Повторная попытка не перезаписывает запись ещё живого процесса.
4. После некорректного завершения доверенный владелец вызывает `TaskProcessRecovery(inbox, owner_scope).recover()` в новом процессе после захвата эксклюзивного SQLite/Workspace lock. Он перечисляет **только свои** nonterminal задачи, читает persisted identity, сверяет `boot_id+start_ticks+sid+pgid` и удерживает Linux **pidfd** на время `SIGTERM`/`SIGKILL` для проверенной process group. Удаляет всех живых членов группы, включая обычных потомков, ждёт подтверждения по `/proc`, затем ставит `CANCELLED` и долговечный `stopped`.
5. При несовпадении личности PID, недоступности pidfd, невозможности проверки группы или отсутствии записи у `RUNNING` — **`held_identity` / `held_unverified` / `held_untracked`**, без опасного сигнала и без освобождения workspace. Никогда не берём произвольный PID из запроса модели.

Важный результат: после успешно проверенного crash cleanup рабочая область снова доступна другой назначенной задаче. Старый delivery ticket остаётся активным/неизвестным до соответствующей ручной обработки, но **не переиздаётся**. `CANCELLED` не является доказательством, что внешний запрос провайдера не был отправлен; исход внешних побочных действий после crash может быть неизвестен. Нельзя повторять такой запрос автоматически.

## Реальные проверки

`python3 -m unittest tests.test_task_process_recovery -v` — **11 новых тестов**, в том числе:

- отдельный доверенный supervisor получает `SIGKILL` в реальном Linux: `worker` остаётся работающим сиротой, SQLite повторно открывается, `recover()` завершает исходную группу и освобождает workspace; после этого та же задача не запускается повторно;
- другая сессия: parent с активным grandchild в его PGID; восстановление выключает всю группу, исключая оставшихся зомби;
- startup gate закрывается до разрешения — downstream код не запускается; при зарегистрированной записи восстановление фиксирует cancelled;
- неправильный `start_ticks` при том же PID означает **HOLD**, работающий процесс не затрагивается;
- отсутствие процесса в реестре при `RUNNING`, чужой owner и обычный `ASSIGNED` без процесса не дают разрешения на сигнал;
- настоящий `pidfd_open` и миграция существующей приватной SQLite из v7 в v8 без удаления задач.

Также повторены старые тесты 5.11 отмены/таймаута, 5.12 ACK/retry, 6.2/6.3 fake provider subprocess. **Полный регресс: 587 unittest OK (1 skipped)**; compileall, source scan, workflow boundaries и staged tree зафиксировать перед публикацией.

## Честные границы

- Восстановление является **явным доверенным bootstrap-вызовом**, не фоновым демоном. Автоматический старт/выкладка на Netcup не выполнялись; встроенные GPT/Claude live-подписки в этой операции не вызывались.
- Управляются потомки, которые **остаются в исходной process group**. Вредоносная программа, специально уходящая через `setsid`/другой cgroup, не покрыта данной гарантией; требуются отдельная ограниченная OS-среда и/или cgroup-супервизия для полностью недоверенного кода. GPT/Claude trusted CLI workers 6.8 пока не имеют такого OS sandbox.
- Recovery не возобновляет неизвестное внешнее действие и не восстанавливает прежний `time.monotonic()` deadline после crash: оно останавливает уже подтверждённую группу, а неопределённые случаи оставляет на HOLD. На Windows/pidfd-less Linux — fail-closed.
- Для зарегистрированных ранее через `attach` direct `Popen` тоже ведётся ledger, но если исходный group leader исчез, а отдельные сбежавшие потомки не видны, безопасность требует ручной разбор. Новый provider path использует стартовый gate.
