# 7.9 — глобальные руководители направлений

Статус на 20.11.2026: **только исходники / offline**. Реальных руководителей
владельцу не назначали; работающий Netcup controller не использует этот модуль.

## Контракт

- Владелец определяет любое направление (`backend`, `qa`, `security` и т. п.),
  конкретного агента и профиль **из уже утверждённого им каталога 7.3**.
- `draft_global_lead(...)` формирует инертную версионированную заявку с
  ожидаемой предыдущей ревизией и SHA-256. Только доверенный owner-authenticated
  ввод `OwnerDecision` с **точным** `proposal_id` и SHA-256 может передать её в
  `approve_global_lead(...)`. Текст агента не считается подтверждением.
- `draft_global_lead_removal(...)` и тот же `approve_global_lead(...)`
  снимают назначение по решению владельца. Замена руководителя — новая
  подтверждённая ревизия, не скрытая смена исполнителя.
- Решения хранятся в приватной task SQLite v16, а не в общей рабочей памяти:
  один ряд на событие, CAS и атомарный коммит, проверяемая цепочка предыдущих
  дайджестов, ревизии и неизменяемый журнал назначения/снятия.
- `load_global_lead(...)` отдаёт действующее назначение только при совпадении
  **текущего** утверждённого каталога; при смене каталога без повторного
  решения владельца — HOLD. После снятия роли возвращает `None`.

**Граница власти:** руководитель направления и проектный оркестратор работают
на равных. Глобальная запись сама по себе **не** меняет project team, task
owner, право на исходники/секреты, делегирование, grants, квоты или процессы.
Работа внутри конкретного проекта требует обычного утверждённого проекта,
допуска участника, плана/задачи и `TaskPermissionGate`.

## Проверка и запуск

Offline-тесты моделируют назначение, замену, снятие и повтор, незарегистрированное
направление, подменённое решение, смену каталога, чужого владельца, stale CAS,
сбой SQLite, tampering, рестарт и миграцию v15→v16; ни один тест не вызывает
модель или Netcup. Полный регресс и CI фиксируются отдельно в отчёте.

До реального использования нужен **работающий** аутентифицированный канал
решений владельца и потребитель справочника ролей в живом оркестраторе;
в существующем controller этого нет. Также перед миграцией установленной
на Netcup task SQLite v14 требуется отдельная проверка deployed backup hook:
настоящий установленный hook не допускает версию v16. Текущий проверенный
source backup также разрешает только v14/v15. Переход требует отдельного
review, совместимого signed backup update и независимого restore smoke.
Ни live migration, ни назначений, ни новых разрешений без отдельной реальной
проверки не выполнять.

Rollback исходника — предыдущий SHA GitHub `main` перед коммитом 7.9;
текущая серверная версия и приватные данные не изменялись.
