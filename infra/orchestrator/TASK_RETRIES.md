# 5.12 — ограниченные повторы, идемпотентность и безопасный resume

**Область:** только программный локальный оркестратор AI Agent Engine,
не существующий Netcup controller и не другие проекты.

## Что реально реализовано

1. **Идемпотентный приём.** Доверенный `TaskInbox.accept(...,
   idempotency_key="...")` привязывает ключ к `(owner_id, project_id)` и
   хешу **всего** содержимого задачи. Повтор с тем же ключом и payload
   возвращает **тот же `task_id`/receipt** даже при заполненной очереди
   и после SQLite restart. Другой payload под тем же ключом отвергается.
   В приватной БД хранятся только SHA-256 ключа и payload, не сырой ключ.
   Без ключа поведение существующего API не изменяется. Уже существующий
   **локальный** `POST /v1/tasks` принимает необязательный заголовок
   `Idempotency-Key`: повтор возвращает тот же `202`/ID/receipt;
   другой payload возвращает `409 idempotency_conflict`, некорректный
   ключ — `422`. Заголовок **не является аутентификацией** и не даёт
   прав: публичное открытие HTTP до этапа 5.13 запрещено.
2. **Долговечные выдачи.** `TaskDeliveryManager.reserve(...)` выдаёт
   один случайный `attempt_token` только **первому** владельцу попытки;
   повторные/конкурентные вызовы возвращают `should_execute=False`
   и **не дают второй исполняемый токен**. Каждая попытка привязана к
   существующему `task_id`, назначенному worker и его workspace.
   Чужой владелец или worker не может зарезервировать/подтвердить её.
3. **Конечный лимит.** Максимум `1..5` попыток на задачу, политика
   фиксируется при первой выдаче, затем не может меняться. По
   подтверждённому отказу `report(..., success=False)` попытка становится
   `retryable` с сохраняемым временем нового запуска (нарастающая
   задержка) или `exhausted` по достижении лимита. Новая попытка
   выдаётся только после задержки и с **новым токеном**. Старые токены
   не допускаются к подтверждению нового результата, повторный ACK
   результата не увеличивает счётчик.
4. **Связь с реальным процессом.** Для первого запуска работает
   `TaskProcessController.attach`. После выхода процесса с ненулевым
   кодом доверенный код вызывает `complete_failed_attempt`, который
   проверяет, что **вся группа действительно остановилась**, и сохраняет
   тот же логический `RUNNING` + эксклюзивный workspace для следующей
   попытки. После ACK отказа и нового ticket можно вызвать
   `attach_retry(..., delivery_token=...)`. Фальшивый токен, живая
   старая группа или не тот worker отклоняются. При успехе **сначала**
   `finish(success=True)` проверяет завершение процесса и фиксирует
   `SUCCEEDED`, **затем** `report(success=True)` подтверждает выдачу.
   Когда исчерпаны попытки, `finalize_exhausted` фиксирует `FAILED`
   **только после проверки остановки**, и workspace освобождается
   после SQLite commit. Отмена в паузе между попытками поддерживается.
5. **Resume после перезапуска.** Приватная task SQLite мигрирует с
   **v1/v2/v3 → v4** одной транзакцией без перемещения, копирования и
   перезаписи уже созданных задач. Сохраняются key→task, номер попытки,
   состояние, дедлайн повторной выдачи и результат. `snapshot` и
   `resume_pending` возвращают только собственные метаданные. Если
   прежняя попытка осталась `active` и её результат неизвестен,
   **повторный запуск запрещён**: после рестарта не выдаётся второй токен.
   Доверенный исполнитель должен сначала согласовать прежний результат
   с сохранённым токеном. После подтверждённого отказа задача снова
   становится `retryable`; это безопасный resume **выдачи**, а не
   автоматическое возрождение упавшего процесса.

## Порядок доверенного исполнителя

1. `accept` с постоянным ключом запроса, `claim_task` на приватный каталог.
2. `reserve` с `max_attempts` и своим закреплённым `worker_id`. **Только
   если `should_execute=True`**, создавать изолированный `Popen`.
3. Первый раз `attach`, при следующей попытке — `attach_retry` с токеном.
4. Успех: `finish(success=True)` → `report(success=True)`.
   Неуспех с живым процессом: дождаться его выхода, проверить
   `complete_failed_attempt` → `report(success=False)` → после задержки
   снова `reserve`. При `exhausted` выполнить `finalize_exhausted`.
5. После restart читать `resume_pending` и сверять результат предыдущей
   выдачи; **не запускать** автоматически старый `active`.

## Ограничения — без ложных гарантий

- Данные одной очереди приватны (`0700`/`0600`); рабочая БД Netcup
  `ai_agent_engine/task_db.py` не меняется. Новая таблица попыток —
  **в той же** task SQLite, второй БД и внешнего сервера нет.
- Это гарантия **одной разрешённой локальной выдачи и отсутствия второй
  автоматической выдачи** на один active ticket, не математическое
  «exactly once» для произвольного внешнего API. Внешний адаптер обязан
  использовать стабильный `task_id` как ключ идемпотентных побочных
  эффектов; неизвестный результат после crash требует сверки.
- Если приложение аварийно завершилось во время выполнения, в памяти
  не остаётся `Popen` handle и watchdog/deadline 5.11; здесь **нет**
  небезопасного восстановления или повторного запуска неизвестного
  внешнего процесса. Полная тестовая проверка crash/concurrency и
  восстановления исполнителя — 5.14, права/grants — 5.13.
- Таймаут `TaskProcessController` 5.11 завершает логическую задачу
  `TIMED_OUT` и не запускает повтор; ограниченный retry в 5.12 работает
  на **подтверждённых отказах отдельной попытки**. Никакого HTTP
  **dispatch/повтора исполнения**, модели GPT/Claude, новых платных API
  или внешних воркеров нет; HTTP idempotent *admission* работает локально.
- Никаких изменений Netcup production, systemd, портов, рабочих секретов,
  клиентских данных и других проектов. Расходов нет.
