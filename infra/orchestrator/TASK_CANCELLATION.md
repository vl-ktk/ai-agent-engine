# 5.11 — контролируемая отмена и таймауты локальных процессов

**Дополнение 6.9 (18.11.2026):** для durable task SQLite v8 при `attach` записываются PID/session/start ticks/boot ID, штатное завершение помечает ledger `stopped`. Новый `launch_gated` не выполняет реальный worker до записи в SQLite. После `SIGKILL` supervisor доверенный [restart recovery](./TASK_PROCESS_RECOVERY.md) идентифицирует прежнюю группу через pidfd и завершает её либо оставляет HOLD без опасного сигнала. Следующий контракт 5.11 ниже описывает исходное, исключительно in-memory управление.

**Проект:** только AI Agent Engine. Это локальный внутренний модуль,
не подключённый к production Netcup, к HTTP API или к платным AI-провайдерам.

## Контракт

- `TaskProcessController(inbox)` управляет **уже созданным доверенным кодом**
  `subprocess.Popen` через `attach(task_id, process, trusted_scope,
  actor_id=worker_id, timeout_seconds=...)`. Не принимает строки команд,
  не создаёт процессы от имени HTTP-клиента и не предоставляет shell/API.
- Процесс обязан быть живым лидером **собственной новой сессии и группы**
  (`start_new_session=True`), чтобы нельзя было случайно послать сигнал
  группе самого движка. Дополнительно проверяются область владельца,
  существующее `ASSIGNED`-назначение и совпадение worker ID.
- `attach` переводит `ASSIGNED → RUNNING` через штатный долговечный аудит.
  Отказавшийся `attach` **не берёт процесс под управление**: запустивший
  его доверенный код обязан завершить его сам.
- `cancel` для `QUEUED/ASSIGNED` фиксирует `CANCELLED` сразу, поскольку
  прикреплённого процесса нет. Для `RUNNING` **без прикреплённого процесса**
  возвращает отказ, не освобождая занятый рабочий каталог.
- Для прикреплённого процесса отмена посылает `SIGTERM` **всей отдельной
  группе**, ждёт короткий grace-period, затем при необходимости `SIGKILL`.
  Проверяется отсутствие живых членов группы в Linux `/proc`, включая
  дочерние процессы, и выполняется `Popen.wait()` для прямого ребёнка.
  Зомби-потомки не считаются выполняющимися процессами.
- Только **после подтверждённой остановки группы** выполняется переход
  `RUNNING → CANCELLED`; SQLite фиксирует статус и обезличенное событие
  аудита атомарно. Workspace `flock` освобождается только после commit.
- Таймаут задаётся в секундах относительно локального монотонного времени,
  проверяется отдельным watchdog-потоком и завершает группу тем же путём,
  затем пишет `TIMED_OUT`. Гонка ручной отмены и таймаута защищена
  блокировкой одной задачи; успешный терминальный переход только один.
- `finish(..., success=True/False)` разрешён только после фактического
  выхода прямого процесса и всех живых членов его группы; `success` обязан
  соответствовать exit code (`0` — успех, иначе ошибка). После дедлайна
  `finish` уже не подтверждает успех — watchdog запишет таймаут.
  Один PID/группа не может принадлежать двум задачам. Это доверенный
  локальный вызов, не публичная команда установить произвольный статус.
- `close()` вызывается **до `TaskInbox.close()`**: останавливает ещё
  прикреплённые процессы, фиксирует `CANCELLED`, ждёт watchdog. При ошибке
  остановки или SQLite возвращает ошибку; ложного успешного ACK нет.

## Сбои, ограничения, эксплуатация

1. Если сигнал, проверка группы или запись SQLite завершились ошибкой,
   терминальный статус **не публикуется**, lease не освобождается. При
   ошибке БД после остановки процесса можно повторить `cancel`; watchdog
   повторяет таймаут и сохраняет обезличенную диагностическую метку
   `timeout_stop_failed` (не более 32 записей).
2. Отсчёт deadline и активная registry процессов остались **в памяти одного
   экземпляра**, но после 6.9 process identity отдельно сохраняется в SQLite.
   Доверенный `TaskProcessRecovery.recover()` позволяет подтвердить исходную
   группу/остановить потомков после crash, **не** возобновляя неизвестный
   запрос или прежний deadline; ambiguous identity остаётся HOLD.
   В [5.12](./TASK_RETRIES.md) добавлены долговечные
   идемпотентные выдачи и ограниченный retry **подтверждённо неудачных**
   попыток, но неизвестный активный процесс после crash не запускается
   повторно автоматически.
3. Это механизм для изолированных Linux-процессов, **не адаптер LLM**,
   не обработчик любых ОС-процессов, не распределённый диспетчер и
   не доказательство работы модели. Не прикреплять произвольные PID:
   требуется собственный `Popen`, созданный доверенным исполнителем.
4. `TaskInbox.transition_state` остаётся внутренним низкоуровневым API:
   сам по себе он не посылает сигналы. Исполнители должны использовать
   контроллер для управляемых задач. Публичного HTTP-cancel нет до
   аутентификации/грантов; нельзя открывать наружу существующий HTTP
   без следующего этапа безопасности.
5. Никаких изменений Netcup, рабочих данных, systemd, портов, секретов
   и других проектов. Никаких серверов, платных API или новых расходов.

## Доказательства

`python3 -m unittest discover -s tests -p test_task_control.py -v`

20 тестов на приватных временных SQLite и каталогах: queued/assigned
cancel, реальное завершение `sleep`-процессов, `SIGTERM`→`SIGKILL`,
уход прямого ребёнка с оставленным живым потомком, watchdog timeout,
гонка cancel/timeout, сохранение терминального статуса/аудита после
restart, освобождение каталога только после commit, отказ на чужом
scope/worker или несепарированной группе, запрет двойного attach одной
группы и успеха после deadline, отдельные параллельные
процессы, закрытие контроллера и восстановление после сбоя SQLite.
