# Согласованная архитектура: кризисные специалисты по узким ошибкам

**Решение владельца:** 19.11.2026, после обсуждения принято предложение ограниченной автоматической эскалации. **Статус:** архитектура + offline-реализация 7.8 от 20.11.2026; live пока не реализован. Зависимые части: 7.7 (дефекты и доказательства), 7.10 (обмен подзадачами), 7.11 (лимиты), этап 8 (независимая QA). Рабочий Netcup не менялся.

## Задача механизма

Исполнитель (например, обычный GPT-специалист) сохраняет исходную задачу и роль ответственного. Если он не может устранить конкретный дефект, главный GPT-оркестратор вызывает уже утверждённого кризисного специалиста (например, Codex для сложной программной ошибки или Claude Code, если это соответствует согласованной матрице). Специалист выполняет **только отдельную узкую диагностическую/исправляющую подзадачу** и возвращает результат исходному исполнителю. Это **не переназначение основной задачи по 7.4** и не даёт GPT права самостоятельно менять владельцем утверждённую команду/политику.

## Утверждённая последовательность

1. Основной исполнитель фиксирует воспроизводимую ошибку: дефект, затронутый артефакт/версию, минимальный контекст, ожидаемый результат, тест и следы предыдущих действий. Секреты не входят в передаваемый пакет.
2. Допустимы **до трёх осмысленных попыток** исправления *одного дефекта* обычным исполнителем. Попытка — новая проверяемая гипотеза/изменение плюс результат независимого теста, а не бессмысленный повтор того же запроса. При неизменной ошибке без прогресса, неретрабельном отказе или неизвестной идентичности процесса допускается более ранняя остановка/эскалация. Каждая попытка ограничена временем, расходом и ресурсами в пределах утверждённой политики; бесконечных циклов нет.
3. Если дефект не устранён, основной исполнитель сохраняет checkpoint; главный GPT обосновывает выбор кризисной специализации по **утверждённой версии команды, политике моделей и навыкам**. Вызов разрешён без нового вопроса владельцу **только** при заранее утверждённых плане, scope, `ActionGrant`, квотах и ограничениях; ядро проверяет всё до запуска. Если необходимы новая роль, модель, проектный scope, дополнительные права, расходы или расширение плана — предварительное согласие владельца обязательно.
4. Кризисный специалист получает минимальную необходимую подзадачу с критерием завершения и контекстом ошибки, **одну ограниченную попытку** решения с проверкой. Исходная задача остаётся за первоначальным агентом; её зависящая от дефекта часть ждёт. Пересечение записываемых workspace и живых процессов запрещено: нужен отдельный sandbox/ветка и безопасная передача проверенных результатов, а не одновременная запись в одни файлы. Передача не наследует чужие grants.
5. При успехе специалист возвращает проверенный patch/артефакт, сведения о тестах и provenance; основной агент сверяет совместимость, при необходимости проводит интеграционные тесты и **продолжает свою исходную задачу**. Успех специалиста сам по себе не означает автоматическую выкладку или принятие всего проекта.
6. Если ограниченная попытка кризисного специалиста не удалась, её результат не проверяем либо требуются расширенные права/внешнее решение — **HOLD + сообщение владельцу** с диагнозом, попытками, сохранённой работой и конкретными вариантами дальнейших действий. GPT не запускает нового кризисного агента по кругу и не повышает полномочия самостоятельно.

## Важные границы и будущая проверка

- Число **три** здесь относится к устранению **одного дефекта основным исполнителем**; не смешивать с тремя попытками подготовки плана из 7.2 и с `attempt_id` целой задачи из 7.4. Обращение к кризисному специалисту — отдельная вложенная подзадача с собственным аудитом, а не переписывание назначения основной задачи.
- Выбор конкретной модели Codex/Claude Code осуществляется утверждённой глобальной матрицей из 7.3; новая специализированная роль требует согласования состава команды. Использовать заранее одобренного специалиста можно без отдельного подтверждения каждого инцидента при неизменности рамок исходного плана.
- Не допускать циклов «GPT → Codex → GPT → Codex» для одного дефекта без нового решения владельца; аварийный hold и отзыв разрешений действуют немедленно. Не повторять необратимые внешние действия вслепую.
- На реализации проверить: не более трёх полезных попыток; ранний отказ при повторяющемся безрезультатном дефекте; корректную изоляцию узкой подзадачи; ровно одну кризисную попытку; возвращение результата исходному агенту; запрет новых грантов/специалистов без approval; эскалацию владельцу после неудачи; отсутствие циклов и перекрывающихся writable-workspace; аудит каждой попытки и независимую QA.

## Проверяемое ядро 7.8 в исходниках (без живого запуска)

`CrisisEscalationCoordinator` из `ai_agent_engine/main_escalation.py` принимает только доверенный Python-контекст `OwnerScope` и уже существующий `ProjectDiagnosticsStore`/`TaskInbox`. Проверяет 1–3 диагностические попытки одного инцидента, approved plan/team/role/provider, отдельную workspace и неизменный owner/project. Создаёт **одну** идемпотентную дочернюю задачу, а 7.3 `assign_specialist` отдельно проверяет существующие task-scoped `ActionGrant` и не создаёт новые разрешения. На кризисной задаче `TaskDeliveryManager` допускает **ровно одну** попытку. Приватная task SQLite v15 хранит связку, переходы и обезличенный аудит; `TaskPermissionGate` запрещает продолжать защищённые действия в `HOLD`. Успех требует завершённой задачи, зафиксированной версии исходников и результата доверенной QA; иначе — `HOLD` и безопасный отчёт для будущего уведомителя владельца. Исходный исполнитель сохраняет свою задачу.

Это **не** запуск нового runtime и **не** автоматическая доставка уведомления: реальные модели, запуск task runner на Netcup, глобальный cost/token quota gate 7.11 и live интеграция восстановления оригинальной задачи пока отсутствуют. Консольной команды, HTTP/MCP, другого сервера, Cloudflare или изменения Windows данный этап не добавляет. 7.8 остаётся `[ ] PARTIAL` до полного live E2E.
