# AI Agent Engine — ChatGPT Web First: блокирующий этап подключения

**Решение владельца 21.11.2026.** Это действующая спецификация для первого шага текущего подпункта **7.11**. Единый источник реализации — `vl-ktk/ai-agent-engine/main`; эта запись **не меняет 11 этапов / 169 прямых подпунктов** и не закрывает 7.11. В приоритете — проверяемый путь к **обычному ChatGPT (Chat, не Codex/Work и не платный API)**. Не объявлять технический прототип доказательством законности, стабильности либо применения лимитов ChatGPT.

## 1. Главный порядок и блокировка зависимых работ

1. **Сейчас: 7.11 / CHATGPT-WEB-FIRST.** Вести только реализацию сменяемого `chatgpt_web` provider adapter и необходимого для него проверочного контура; существующий `gpt_siwc` сохранять без изменений. Допускаются исключительно относящиеся к этому шлюзу регрессионные тесты и исправления обязательных зависимостей (TaskInbox, SharedCapacity, TaskPermissionGate, ChatManager, scoped memory).
2. **Контрольная точка A — OFFLINE.** Реализовать адаптер, выключенный по умолчанию, на mock/fake UI; доказать маршрутизацию, изоляцию, смену чатов, повторную доставку без двойного выполнения, восстановление, конфигурацию модели/усилия и безопасные отказы.
3. **Контрольная точка B — LIVE/POLICY.** Отдельно проверить техническую реализуемость, текущие правила OpenAI и применимость именно лимитов обычного ChatGPT. Любое взаимодействие с личной учётной записью, cookies, токенами, действующим браузером или автоматизированное извлечение ответов — только после отдельного решения владельца и проверки допустимости. Одно согласие владельца само по себе не отменяет условия сервиса.
4. **Контрольная точка C — GATE.** Только при подтверждённом `TECH_GO` **и** `POLICY_GO` разрешить дальнейшую разработку механизмов, зависимых от обычного ChatGPT, и интеграционные E2E. В противном случае `HOLD/NO-GO`, зафиксировать факты и варианты для владельца. Скрытого перехода на SIWC/Codex/Work/платный API нет.
5. **Только затем** вернуться к остальной незавершённой части 7.11 (включая численные production-лимиты и решение о SQLite v14→v17), затем по исходному порядку к 7.12–7.14, этапам 8–11. Независимые ранее принятые результаты не пересоздавать, но и не считать их подтверждением Web ChatGPT.

**Стоп-условие:** до A+B+C не переносить фокус на школу, университет, расширение UI, новые роли или другие будущие функции. Разработка самого тестового каркаса для подтверждения подключения разрешена. Для production нужна собственная отдельная приёмка и разрешение владельца.

## 2. Контракт одного адаптера

- `provider_id=chatgpt_web`, `enabled=false` по умолчанию, отдельная конфигурация без доступа к секретам через Git. Существующие provider-neutral интерфейсы не ломать.
- Отдельные устойчивые `agent_id`, `project_id`, `chatgpt_project_id`, `conversation_id`, `model_id`, `reasoning_effort`, `instruction_revision`, `checkpoint_id` и `task_id`; связь IDs хранит сервер, не имя чата.
- Создать **новый чат внутри того же ChatGPT Project**, проверить членство до отправки. При отсутствии подтверждённого project context — `HOLD`, не создавать чат в корне и не отправлять данные в чужой проект.
- Настройка модели и уровня рассуждений — по конкретному агенту/задаче; перед запросом проверять фактическую применимость, не подменять тихо на другой режим. ChatGPT UI и лимиты изменчивы; `reasoning_effort` не считать документированной API-гарантией для веб-чата.
- Подготовка контекста: актуальные инструкции ChatGPT Project, роль, грант, краткое проверенное состояние задачи, релевантная scoped-память. Без переноса скрытых рассуждений или полного архива в промпт.
- Авто-ротация чата: soft checkpoint приблизительно 60% контекстного бюджета, плановый переход около 75%, аварийный около 90% — **только регулируемые эвристики**, поскольку точный веб-счётчик токенов может быть недоступен. При смене чата сохранять очередь и связь `old_chat→new_chat`; task id и agent id не меняются.
- `Request/Response` контракт: correlation ID, один идемпотентный task lease, delivery receipt, error type, model/effort evidence если доступно, rate-limit/retry-after, timestamps и audit без ответов/секретов. Не перепутывать получение ответа с успешным исполнением действия.
- `HOLD` при auth failure, CAPTCHA/anti-bot challenge, UI drift, неизвестной модели, лимите, невозможности определить ChatGPT Project или подтверждение выполнения. Никаких обходов защит, скрытых повторов, массового параллелизма или выдачи `PASS` по mock результату.

## 3. Проекты, роли и связь с ядром

- Единое постоянное серверное ядро: ChatManager/registry, TaskInbox/TaskPermissionGate, SharedCapacity, MessageBus, MemoryStore, InstructionManager, audit. Отдельный процесс сервера/SQLite на каждый чат не требуется.
- Главный ИИ-оркестратор имеет собственный ChatGPT Project и цепочку чатов; проектные руководители, руководители направлений, рабочие агенты, школа и университет — свои одобренные проектные пространства и те же правила ротации.
- Роли не порождают прав: только owner-approved project/team/task/grants. Главный оркестратор планирует и делегирует через ядро, а ядро исполняет проверки. Глобальный руководитель не становится начальником чужого проекта автоматически.
- Project-only memory в ChatGPT включается **отдельно в каждом проекте** и является только контекстной изоляцией UI; реальную защиту обеспечивают серверные scoped access, SQLite/workspace и разрешения.
- Агенты обмениваются задачами/вопросами/результатами через долговечный `MessageBus`, а не магической прямой связью чатов. Сообщения сохраняются независимо от `conversation_id`, имеют ID, срок и статус, повторяются безопасно, маршрутизируются только по scoped grant и журналируются.

## 4. Память, общие знания и обучение (после прохождения Web Gate)

- На сервере — проектная/агентная/задачная память и полный журнал с происхождением; проверенные инструкции и решения — версионируемый источник; резервные копии и восстановление тестировать отдельно.
- Смена чата оркестратора, руководителя, исполнителя, ученика и исследователя едина: новое окно внутри того же ChatGPT Project, только необходимый проверенный bootstrap, старое сохраняется в истории.
- Универсальные **проверенные** методы и воспроизводимые исправления можно публиковать в общую owner-scoped базу знаний по утверждённым правилам. Закрытые чаты, исходники, файлы и секреты не становятся общими автоматически. Особое раскрытие проектных данных требует отдельного scoped разрешения; всё логируется.
- AI School: обучающие агенты на доступном Instant, проверяемые задания и результаты; это накопление навыков, инструкций и памяти, **не обучение весов** модели и не обещание бесконечных запросов.
- AI University: высокий доступный уровень рассуждений только для семейств проблем с **тремя подтверждёнными содержательными неудачами** в школе и/или проектах суммарно. Смена чата, дубль retry или разные формулировки одной попытки счётчик не повышают. Система сверяет семейства ошибок по приватному нормализованному ID, но подробности каждого инцидента остаются scoped; университет получает разрешённую карточку с воспроизводителем, не blanket-доступ к проектам.
- Университет возвращает независимо проверенное решение в общую библиотеку/школу/рабочие проекты. Автоматически менять права, системные правила или продакшен по результату обучения запрещено.

## 5. Проверки и критерии готовности

### Контрольная точка A — OFFLINE (может выполняться сейчас)

- Adapter `enabled=false`; mock-browser на тестовых фикстурах; никаких live личных сессий.
- Положительный кейс: два агента с разными проектами/чатами, выбор моделей/усилия, сообщение, ответ, доставка/ack, смена чата внутри нужного проекта, восстановление очереди после crash.
- Отрицательные кейсы: неверный project ID, чужой grant, истекший lease, противоречивый model/effort, UI drift, rate-limit, неожиданный пустой ответ, двойная доставка, сбой между записью эффекта и ack. Fail-closed без межпроектных утечек и без повторной публикации.
- Проверить сохранение точных версий, входного коммита, подписанного approval workflow; CI/юнит/интеграционные тесты PASS или честный FAIL.

### Контрольная точка B — LIVE/POLICY (отдельный запрос)

- Проверить и задокументировать **допустимый** реальный путь доступа, а не только способность открыть UI. Подписка Plus не равна API, а официальный SIWC не доказательство расхода лимитов обычного Chat.
- Если разрешённый способ существует: отдельное owner-approved короткое исследование в изолированной среде, без обхода rate-limit/защит и без передачи credentials в логи/репозиторий; доказать проект, модель/effort, получение ответа, смену чата, лимиты и возобновление.
- Если приемлемого способа нет — `POLICY_HOLD/NO-GO`; сообщить владельцу, не изображая завершённый продукт. Никаких живых ChatGPT web-автоматизаций только на основании этой записи.

### Контрольная точка C — решение

- Записать независимые статусы `TECH_GO|HOLD|NO-GO` и `POLICY_GO|HOLD|NO-GO`; `INTEGRATION_GO` только если оба GO.
- Зафиксировать протокол, тесты, ожидаемые реальные лимиты (если измеримы), остаточные риски, доступный rollback и решение владельца. Без `INTEGRATION_GO` не начинать зависимые задачи, но не удалять существующие наработки.
