# Этап 4.15 — приватное хранилище проектов Netcup

**Статус:** LIVE PASS, 17.11.2026. **Источник:** `vl-ktk/ai-agent-engine`, `main`. Это разметка каталогов и контракт владения файлами; БД, секреты, резервирование и исполнение проектных задач в этот подпункт не входят.

## Фактическая структура на VPS

Хост: `v2202611460959561466`, Debian 13. Общий корень `/var/lib/ai-agent-engine` до изменения был пустым, имел владельца `ae-runtime:ae-runtime` и режим `0700`. Под ним созданы три каталога:

| Назначение | Абсолютный путь | Владелец / группа | Режим |
| --- | --- | --- | --- |
| Постоянные данные/метаданные проектов | `/var/lib/ai-agent-engine/projects` | `ae-runtime:ae-runtime` | `0700` |
| Временные рабочие копии для исполнителей | `/var/lib/ai-agent-engine/workspaces` | `ae-runtime:ae-runtime` | `0700` |
| Результаты и выходные файлы задач | `/var/lib/ai-agent-engine/artifacts` | `ae-runtime:ae-runtime` | `0700` |

**Модель владения для будущих проектов:**
- При **отдельно разрешённом подключении проекта** применять стабильный явно утверждённый `project_id`, а не угадывать имена по URL/названиям. Возможные дочерние пути: `projects/<project_id>`, `workspaces/<project_id>`, `artifacts/<project_id>`.
- Будущие дочерние каталоги — `ae-runtime:ae-runtime`, режим `0700`; файлы по умолчанию не должны быть доступны группе или прочим (например, процессу с `umask 077`). Раздельные места хранения не отменяют обязательной программной авторизации по `project_id`.
- `ae-deploy` — учётка доставки, **не** владелец пользовательских данных и не имеет прямого чтения внутри корня runtime; `root` остаётся администратором VPS. Код контроллера отдельно расположен под `/opt/ai-agent-engine`, эти файлы в 4.15 не менялись.
- Это **не OS-изоляция разных проектов**: все будущие папки с владельцем `ae-runtime` доступны любому процессу того же Unix-пользователя. Для независимых доверительных границ нужны дальнейшие RBAC/изоляция процесса, которых в 4.15 ещё нет.
- Не разрешать произвольные имена с `..`, `/` или симлинками для формирования пути; проверки идентификаторов и ссылок реализуются вместе с проектным API на следующих этапах.

## Идемпотентное воспроизведение

На согласованном VPS под администратором применены отдельные команды. Повторный запуск не требует чистить данные и восстанавливает режим и владельца каталогов:

```bash
install -d -m 0700 -o ae-runtime -g ae-runtime /var/lib/ai-agent-engine/projects
install -d -m 0700 -o ae-runtime -g ae-runtime /var/lib/ai-agent-engine/workspaces
install -d -m 0700 -o ae-runtime -g ae-runtime /var/lib/ai-agent-engine/artifacts
```

Команды рассчитаны на **существующий** `ae-runtime` и приватный корень `/var/lib/ai-agent-engine`. Перед использованием на другом сервере проверить, что эти пути — настоящие каталоги, а не символические ссылки или чужой mount; не применять вслепую к произвольным путям с данными.

Netcup SCP root VNC, 17.11.2026:

1. До создания: `stat` корня → `directory ae-runtime:ae-runtime 700`; `ls -la` → только `.`/`..`.
2. После создания и повторного применения: `stat -c '%U:%G %a %n' /var/lib/ai-agent-engine/{projects,workspaces,artifacts}` → **каждый** `ae-runtime:ae-runtime 700`.
3. `runuser -u ae-runtime -- ls -ld /var/lib/ai-agent-engine/projects` → `drwx------`, успешный доступ.
4. `runuser -u ae-deploy -- ls /var/lib/ai-agent-engine/projects` → `Permission denied` (ожидаемый отказ).
5. `systemctl is-active ae-controller.service` → `active`; `systemctl --failed --no-pager` → `0 loaded units listed`.

**Не выполнялось:** создание дочерних каталогов конкретных проектов; запись проектных данных; перезапуск контроллера; тест полной перезагрузки VPS; проверка OS-изоляции одного проекта от другого.

## Откат и защита данных

До 4.15 этих трёх дочерних каталогов не было; предыдущий подтверждённый режим корня уже был `0700`. Для возврата к прежней структуре администратор **сначала** должен отдельно убедиться, что конкретные дочерние каталоги пустые и никто не начал их использовать; только после явного разрешения владельца возможно точечное `rmdir` трёх именованных пустых каталогов. **Не применять рекурсивное удаление, не менять общий runtime-корень.** GitHub-документацию откатывать по предыдущему commit SHA из отчёта; приложение `ae-controller` и его релиз в 4.15 не изменялись.
