## Зачем

Владелец хочет максимально простой и быстрый постоянный способ для GPT самостоятельно
обслуживать **существующий** Netcup VPS: устанавливать пакеты и приложения,
обновлять AI Agent Engine, настраивать Linux, проверять службы и логи,
исправлять сбои, делать резервные копии, запускать тесты и откатывать релизы.
Не строить для этого новый сервер, отдельный MCP или сложный набор отдельных
прав на каждую операцию. Не повторять обсуждение выбора архитектуры после
восстановления этой задачи.

## Что сделать, без лишней инфраструктуры

1. **Разовый административный вход в существующий Netcup** через
   подтверждённую консоль владельца. Перед правками снова проверить
   работающий релиз, сохранить его точный SHA и состояние служб/данных.
2. **Создать один постоянный канал полного администрирования**:
   существующий `ae-deploy` через SSH + возможность `sudo` без ввода пароля.
   Это выбор владельца ради оперативности, **не выполненное действие**.
   Не включать прямой root SSH и не отправлять пароли/приватные ключи в чат.
3. **Доработать GitHub Actions / GitOps** для инициирования из ChatGPT
   административных заданий и получения результатов: выполнение команд,
   управление пакетами/службами, просмотр логов, развёртывание и откат.
   Ограничивать запуск доверенным владельческим источником и защищёнными
   workflow; не исполнять произвольный код из PR, непроверенного коммита или
   непроверенного внешнего текста. Существующий SSH-ключ и pinned host key
   сохраняются. Все команды и исходы должны попадать в журнал.
4. **Проверить живым прогоном**, а не только CI: read-only статус →
   безопасная административная команда → установка тестового компонента →
   перезапуск разрешённой службы → health-check → откат. Перед публикацией
   повторно сверить состояние Netcup и GitHub HEAD, чтобы не затереть
   параллельные изменения.
5. **Подтвердить работу без браузера и ПК владельца.** Если доступ не
   осуществляется прямо из текущего ChatGPT через подключённые инструменты,
   считать блокером, а не объявлять систему автономной.

## Границы и риски

Полный `sudo` у `ae-deploy` **эквивалентен root** для обладателя ключа,
который может инициировать соответствующий workflow. Это сознательный
компромисс владельца: удобнее и шире, но при компрометации GitHub/ключа
потенциально может быть уничтожен весь VPS и данные.

- Не менять секреты, SSH-права, sudoers и рабочие данные, не делать
  необратимых удалений и не публиковать непроверенные изменения
  без соответствующего разрешения владельца.
- Изолировать права запуска привилегированного workflow; не открывать
  произвольный root-runner для любых push/PR. Проверять актор, ветку,
  точный исходник и неизменность host key.
- Использовать существующие локальные резервные копии, понимать, что
  **полное уничтожение VPS может уничтожить и эти копии**; независимого
  offsite-бэкапа подтверждено не было.
- Секреты не записывать в репозиторий, чат, архивы или логи.
- Ранее предложенный отдельный подписанный релизный оператор
  (`infra/deploy/GITOPS_NETCUP_CONTROL.md`) остаётся в коде; решение о
  его использовании/замене принимается при безопасной настройке одного
  административного канала, без дублирования инфраструктуры.
