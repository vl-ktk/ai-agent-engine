**Внимание к дополнительным файлам:** после SQLite-проверки рядом с некоторыми
снимками появляются `engine.sqlite3-wal` (0 B) и `engine.sqlite3-shm` (32 KiB).
Они не входят в `manifest.json` и **не являются** частью набора для переноса;
не копировать их как рабочие файлы. Причина их появления не установлена.

Backup-код создаёт SQLite через SQLite **online backup API**, файлы через
`tar.gz`, проверяет SHA-256, `PRAGMA integrity_check` и содержимое архива,
атомарно публикует снимки и сохраняет не более **7 копий / 2 GiB**. В архив
**не включены** секреты `/etc/ai-agent-engine/secrets`, SSH-ключи/доступы,
настройки Netcup/файрвола, OS-пакеты, systemd units, релиз контроллера,
журнал и полноценный образ диска. GitHub хранит код, **не рабочую БД**.

## 2. Критическое ограничение и сценарии отказа

| Отказ | Что реально можно сделать сейчас |
| --- | --- |
| Потеря/порча отдельного файла при живом VPS | Выбрать локальный снимок и восстановить **сначала в отдельный каталог**, согласно [4.19](./RESTORE_SMOKE.md) и [4.20](./RESTORE_FILES_SMOKE.md). Замена рабочих данных — отдельное согласованное действие |
| Не загружается ОС, но старый диск ещё читается | Не переустанавливать и не форматировать исходный диск. Если доступно санкционированное read-only восстановление, сохранить снимок на независимый носитель с проверкой контрольных сумм; затем следовать шагам ниже. Доступность этого пути не проверялась |
| Утерян весь VPS/диск, а независимой копии нет | **Данные не восстанавливаются из GitHub и локальных копий.** Можно пересобрать код/конфигурацию, но нельзя вернуть потерянную рабочую SQLite, файлы и секреты. Это текущее ограничение, пока не создана независимая копия |
| Утерян весь VPS/диск, имеется проверенная внешняя копия | После решения владельца о целевой машине и безопасной передаче — восстановление по шагам 3–5. **Такой сквозной live-тест пока не выполнялся** |

**Нет настроенного в рамках AI Agent Engine off-host резервирования.** Локальные
снимки находятся **в том же домене отказа, что и исходные данные**: потеря
диска/аккаунта/сервера может уничтожить всё сразу. Netcup console, GitHub
source и GitHub CI не являются запасным хранилищем рабочей БД.

## 3. Инвентаризация и read-only диагностика (на работающем VPS)

Команды выполняются авторизованным администратором, **ничего не удаляют**.
Не печатать содержимое БД, manifest, секретов и stdout диагностических
скриптов, содержащий токены, в публичные логи.

```bash
date -u
cat /etc/debian_version
readlink -f /opt/ai-agent-engine/current
systemctl list-unit-files 'ae-*' --no-pager
systemctl is-active ae-controller.service ae-backup.timer ae-host-check.timer
systemctl list-timers ae-backup.timer --no-pager
ls -ld /var/lib/ai-agent-engine /var/backups/ai-agent-engine
ls -1 /var/backups/ai-agent-engine/
sha256sum /usr/local/libexec/ae-backup.py /etc/systemd/system/ae-backup.service /etc/systemd/system/ae-backup.timer
runuser -u ae-runtime -- python3 /usr/local/libexec/ae-backup.py verify
```

`verify` подтверждает **только новейший** локальный снимок; оно может создать
SQLite sidecar-файлы рядом с копией (ситуация зафиксирована на живом VPS).
Список снимков может меняться по мере ротации; не полагаться на пример ID выше.

## 4. Восстановление после **полной** утраты диска, если внешняя копия уже есть

**Стоп-условия перед любыми изменениями:** владелец выбрал **уже разрешённый**
целевой ресурс; подтверждены доступ и происхождение внешней копии; нет
работающих данных, которые будут затёрты; сохранены SHA релиза и копии;
план отката согласован. **Не покупать новый VPS/хранилище, не менять ключи,
секреты или права доступа автоматически.** Если исходный сервер ещё жив,
не выполнять аварийную выкладку поверх него.

1. **Подготовка чистой системы.** Восстановить одобренную конфигурацию ОС
   (Debian 13), отдельные `ae-deploy`/`ae-runtime`, SSH key-only, сетевые
   ограничения, проверенные корни `/opt/ai-agent-engine`,
   `/var/lib/ai-agent-engine`, `/var/backups/ai-agent-engine`. Инструкции:
   [развёртывание](../deploy/README.md),
   [структура хранилища](../storage/PROJECT_LAYOUT.md). Если подготовка требует
   изменения доступов, ключей или секретов — **отдельная команда владельца**.
2. **Вернуть исполняемый код, не путать его с данными.** Из GitHub получить
   **точный** исходник SHA `85375103800845eeff696e53f510c66c428408ed`
   для live-контроллера; перепроверить `release-manifest.json` и wheel SHA-256.
   Если исторический wheel недоступен, пересобрать его из того же commit
   с собственными проверками — **не считать новую сборку побайтно равной**
   прежней без хеш-сверки. Для контроллера применить защищённые `verify`,
   `stage`, `promote --expected-current NONE` из
   [`promotion.py`](../deploy/promotion.py) **только на пустом новом ресурсе**;
   сохранить результат каждого шага. Установить сверенные root-owned units
   `ae-controller.service`, `ae-host-check.{service,timer}` и
   `ae-backup.{service,timer}`, backup-код из GitHub. Перед запуском:
   `systemd-analyze verify` и сравнение SHA. Пока данные не восстановлены,
   **не включать** controller/timers.
3. **Вернуть снимок на новый сервер безопасно.** Передать **только через
   согласованный защищённый канал** внешнюю копию в приватный staging, без
   публикации в GitHub. Проверить внешний хеш и происхождение, что каталог
   снимка не симлинк, owner/mode и точный набор `engine.sqlite3`,
   `files.tar.gz`, `manifest.json`. После проверки разместить выбранный снимок
   в `/var/backups/ai-agent-engine/<точное-имя>` с владельцем `ae-runtime`,
   каталогами `0700` и обычными файлами `0600`. Не заменять существующие
   каталоги/данные; если путь занят, **STOP**. От имени `ae-runtime` запустить
   `python3 /usr/local/libexec/ae-backup.py verify` и получить `PASS`.
   Замечание: CLI проверяет *последний по имени* снимок; для выбранного
   более старого снимка нужна отдельная проверка через код
   `LocalBackup.verify(Path(...))` после проверки его точного пути.
4. **Сначала изолированная репетиция.** На том же **новом** сервере задать
   `AE_SNAPSHOT` только на точный проверенный каталог и выполнить следующие
   операции **в новый пустой путь** (как в 4.19):

   ```bash
   AE_SNAPSHOT=/var/backups/ai-agent-engine/20261118T100456.636455Z-6da03b65
   test -d "$AE_SNAPSHOT" && test ! -L "$AE_SNAPSHOT" || exit 1
   AE_STAGE=$(mktemp -d /var/tmp/ae-disaster-check.XXXXXXXX)
   test -d "$AE_STAGE" && test ! -L "$AE_STAGE" || exit 1
   tar -tzf "$AE_SNAPSHOT/files.tar.gz"
   cp --no-clobber "$AE_SNAPSHOT/engine.sqlite3" "$AE_STAGE/engine.sqlite3"
   tar -xzf "$AE_SNAPSHOT/files.tar.gz" -C "$AE_STAGE" --no-same-owner
   cmp "$AE_SNAPSHOT/engine.sqlite3" "$AE_STAGE/engine.sqlite3"
   tar -dzf "$AE_SNAPSHOT/files.tar.gz" -C "$AE_STAGE"
   sqlite3 "$AE_STAGE/engine.sqlite3" 'PRAGMA integrity_check; PRAGMA user_version;'
   ```

   В приведённой строке `AE_SNAPSHOT` **пример исторического ID**, заменить
   на фактически переданный проверенный снимок. **До** распаковки проверить,
   что каждый путь в `tar -tzf` относится к
   `projects/`, `workspaces/`, `artifacts/`, не содержит `..`, абсолютных
   имён, символических ссылок и спецфайлов; при сомнениях — **STOP**.
   `LocalBackup.verify` делает такое структурное чтение архива до PASS.
   `sqlite3` должен вернуть `ok` и согласованную версию схемы; ожидаемая
   для снимка 18.11.2026 — `user_version=2`. Не очищать `AE_STAGE` автоматически.
5. **Переключение только после отдельного разрешения на данные.** Убедиться,
   что **целевой runtime-корень на новом VPS пуст**, а никакая служба не
   использует его. Тогда под контролем оператора перенести SQLite с mode
   `0600` и деревья из `AE_STAGE` в три каталога `ae-runtime:ae-runtime /0700`
   **без перезаписи существующих файлов**. Повторить побайтовое сравнение и
   `PRAGMA integrity_check`, проверить содержимое/права/владельца. После
   этого запустить `ae-controller.service`, выполнить его health-check от
   `ae-runtime`, проверить `journalctl` и `systemctl --failed`, затем
   `systemctl enable --now ae-host-check.timer ae-backup.timer`; наблюдать
   успешное резервирование/новый снимок. **Не считать выключенный таймер
   или `ae-backup.service` в состоянии `inactive` отказом**: oneshot service
   запускается таймером.

При неудаче на шагах 1–4 **не переключать** рабочие службы и данные. После
неудачного шага 5 остановить только затронутые службы, сохранить staging,
журнал и прежний точный release SHA; возможный откат *релиза* — только
`promotion.py` compare-and-swap с `--expected-current`, если старый релиз
вообще существует. Не удалять снимки, не применять `git reset --hard`,
не делать `rm -rf` и не трогать иные проекты/сервера.

## 5. Нужное для настоящей защиты от смерти VPS (предложение, не выполнено)

1. Владелец выбирает **второй независимый, уже доступный ему** носитель или
   хранилище вне Netcup VPS — например, имеющийся офлайн-диск/другой
   контролируемый компьютер или уже оплаченный им независимый storage.
   Ни одна услуга здесь не заказана. Хранилище на том же VPS, второе имя
   каталога или GitHub-репозиторий **не подходят**.
2. Подтвердить защищённый, **зашифрованный до передачи** перенос снимков,
   отдельное хранение ключа дешифровки, защиту от случайного удаления,
   права доступа и точный график. Из `manifest.json` проверить SHA-256 всех
   трёх штатных файлов после копирования. **Не помещать секреты/данные в GitHub**;
   не публиковать снимок без согласия и выбранного владельцем назначения.
3. Периодически выполнить реальное восстановление **из независимой копии**
   в изолированный каталог на другом доступном устройстве и проверить
   SQLite, архив и файлы, зафиксировать дату, RPO/RTO и доступность ключа.
   Пока этих действий не было, при полной потере сервера **RPO/RTO не
   обеспечены**. Ежедневное локальное расписание не обещает восстановление
   при общей потере VPS.
