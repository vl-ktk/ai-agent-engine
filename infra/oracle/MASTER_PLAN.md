# Oracle Always Free — отдельный инфраструктурный план (пилот)

Дата начала: 2026-11-20. Авторизация: прямое поручение владельца создать отдельную ветку и план подготовки Oracle.
Ветка: `infra/oracle-setup`. Исходная точка: `main` @ `d79f40d472ce8e2e0848b1b130123f8315786fb4`.

## Цель и неизменные границы

Подготовить один или два независимых Oracle Always Free ARM-сервера для будущей работы AI Agent Engine, управляемых через безопасный механизм OCI/MCP, **без вмешательства в текущую разработку и работающий Netcup**.

- Это автономный инфраструктурный пилот **по отдельному поручению владельца**, а не замена или редактирование общего `IMPLEMENTATION_ROADMAP.md`. Основная разработка остаётся на `main`, этап 7.7 — у своего исполнителя.
- Пока нет отдельного разрешения: не менять `main`, Netcup, Windows, AIE-код, работающую БД и данные; не делать production deployment, миграцию, переключение DNS или выключение Netcup.
- Никаких платных ресурсов, Pay As You Go, списаний, платных API и повышения квот без отдельного решения владельца. Каждый инстанс должен быть однозначно **Always Free eligible**, включая boot volume, сеть и выбранную ОС.
- У каждого аккаунта Oracle свой владелец и отдельный tenancy. Доступ использовать лишь в пределах выданного разрешения; аккаунты **не сливаются** в один, а координируются поверх сети.
- Пароли, private keys, API tokens, OCID с персональными сведениями, IP-адреса с чувствительным контекстом и конфигурации аутентификации не коммитить: репозиторий публичный.
- Внешний MCP-эндпоинт и root/OCI write-доступ не открывать без аутентификации, TLS, минимальных IAM-разрешений, журнала действий и отдельных согласований на опасные операции.
- Каждый шаг: входные факты → действие → проверка → запись в `PROGRESS.md` и `HANDOFF.md` → краткий отчёт владельцу. Следующий шаг — только по его поручению. Статус `[x]` лишь при проверенном результате.

## Порядок выполнения

### OR-0. Изоляция процесса — документация
- **Результат:** отдельная ветка, этот план, фактологический журнал, шаблон конфигурации и локальная записка передачи.
- **Проверка:** SHA ветки и файлы доступны в GitHub; `main` не менялся; GitHub Actions на push этой ветки не управляют Netcup.

### OR-1. Read-only инвентаризация Oracle (первый tenancy)
- Убедиться в личности выбранного tenancy, **home region**, статусе Free Trial/Always Free, текущих инстансах и квотах, блок-томах и биллинге. Отдельно проверить доступность ARM A1 в home region.
- **Результат:** подтверждённая безопасная конфигурация VM и лимитов, отсутствие незапланированных расходов.
- **Проверка:** скриншоты/состояния Console, без раскрытия секретов; отметить доступное и недоступное. Не считать экран создания VM фактом её создания.
- **Стоп:** регион не home, форма показывает стоимость, платный shape, недостаточная квота/ёмкость или неясный биллинг.

### OR-2. Первый Oracle VM — только Always Free
- После OR-1 создать **один** A1 ARM-инстанс подходящей Free Eligible ОС, с минимально необходимым диском, безопасным SSH-ключом и сетью. Параметры CPU/RAM выбирать по текущим подтверждённым лимитам tenancy; не полагаться на устаревшие рекламные цифры.
- **Результат:** первый VM в состоянии RUNNING.
- **Проверка:** shape/OCPU/RAM/диск/метка Always Free/region/public или private IP, счётчики квот, загрузка ОС, ограниченный вход.
- **Стоп:** Out of host capacity означает подождать/проверить AD, а не переходить на платный тариф.

### OR-3. Защищённая базовая настройка VM1
- Обновления, отдельный администратор без повседневного root, ключевой SSH, firewall/OCI NSG, безопасный outbound, time sync, логирование, наблюдение CPU/RAM/disk/network, audit.
- **Результат:** воспроизводимый и минимально открытый сервер; шаблоны настройки в `infra/oracle/setup/` после ревью.
- **Проверка:** доступ есть с разрешённого адреса; лишние порты закрыты; повторная проверка бесплатных ресурсов; сценарий восстановления доступа.
- Не менять SSH/security policy при риске отрезать доступ без рабочего восстановления.

### OR-4. Управление OCI и MCP (сначала read-only)
- Проверить готовые официальные Oracle MCP проекты и совместимость с текущим клиентом ChatGPT; официальный `oracle/mcp` — **reference / не production-ready по заявлению авторов**. Не обещать, что его установка сама подключит инструменты к чату.
- Спроектировать один защищённый управляющий endpoint, локальный OCI auth / короткоживущий токен, минимальный IAM и аудит. Отдельно выбрать SSH/Ansible или OCI Run Command для действий *внутри ОС*; возможности зависят от образа.
- **Результат:** реально зарегистрированный и проверенный удалённый инструмент управления, сначала с командами чтения, без доступа к секретам.
- **Проверка:** пробное чтение tenancy/VM через интеграцию именно из пользовательского клиента; отказ в лишних правах. Разрешение на запись — отдельное решение.

### OR-5. Второй Oracle tenancy и VM2
- С согласия владельца соответствующего аккаунта отдельно проверить его home region, доступные Free-ресурсы и создать независимый VM2 по OR-1…OR-3.
- **Результат:** две управляемые, **разные** VM, ни одна не скрыта за чужой учёткой.
- **Проверка:** независимое подключение и биллинг, уникальные хосты, отказ одного не нарушает управление другим.
- Второй аккаунт не является расширением лимита первого tenancy.

### OR-6. Один управляющий адрес для двух VM
- Одна контрольная точка/HTTPS endpoint маршрутизирует команды на два разных узла или tenancy с отдельными ролями и правами. Приватное соединение между VM и allowlist, никакого общего публичного SSH для всех.
- **Результат:** управляемая связка с одним входом, без иллюзии «общего RAM/CPU» и без общей SQLite через WAN.
- **Проверка:** статус обоих узлов, отказ/возврат одного, запрет cross-tenant доступа. Отказоустойчивость шлюза — отдельный риск (single point of failure).

### OR-7. Независимые резервные копии и восстановление
- Выбрать разрешённое и бесплатное хранилище в допустимых лимитах или использовать уже согласованное, не полагаясь на сами две VM. Периодичность и retention — после оценки фактических данных.
- **Результат:** проверяемый путь восстановить конфигурацию/данные, без самонадеянности «второй сервер = бэкап».
- **Проверка:** тестовое восстановление в изоляции, checksums, SQLite integrity, записи о RPO/RTO и стоимость = 0 в подтверждённом лимите.

### OR-8. Аудит совместимости AI Agent Engine (только чтение)
- Прочитать актуальную архитектуру/код **из утверждённого источника `main`** и текущий `HANDOFF.md` без изменения AIE. Проверить ARM64, Linux-дистрибутив, зависимости, systemd, SQLite single-writer, storage, Docker/пакеты, MCP adapters, границы GPT/Claude/API, сеть.
- **Результат:** список несовместимостей Netcup x86 → Oracle ARM, точные ограничения, схема «один core + второй worker/backup» или обоснованная альтернатива.
- **Проверка:** read-only audit и отдельный отчёт; код `main` и Netcup без изменений.

### OR-9. Изолированный staging AIE на Oracle
- Только после явного согласования: запустить **копию тестового окружения** с синтетическими данными, не production и без live клиентских секретов. Никаких несанкционированных платных моделей.
- **Результат:** измеренные CPU/RAM/IO/latency и жизнеспособный процесс восстановления/перезапуска.
- **Проверка:** reproducible tests, health, alerts, нагрузка, перезапуск VM, отсутствие влияния на Netcup.

### OR-10. Решение о переносе (отдельный owner gate)
- Сравнить измерения, стоимость, риск idle reclaim, доступность OCI, потери gateway и состояние резервных копий. Подготовить staged cutover и rollback без удаления Netcup.
- **Результат:** документ GO/NO-GO, а не автоматический перенос.
- **Проверка:** владелец отдельно принимает решение о деплое и будущем отказе от платного VPS.
