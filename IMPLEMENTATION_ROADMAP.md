В выполненном пункте фиксировать дату, проверку, версию/коммит или другой артефакт, а также ограничения. Ни один пункт не выполнен автоматически от того, что он записан.

**Обязательное правило владельца от 2026-11-17 — строго по порядку:** нельзя переходить к следующему пункту или подпункту, пока предыдущий не выполнен **полностью и не принят**, если приёмка предусмотрена. При блокере оставаться на том же пункте, записывать `PARTIAL`/`BLOCKED` и запрашивать необходимое решение — не переходить к соседней задаче. Подробные обязательные инструкции для любого исполнителя — [`AGENTS.md`](./AGENTS.md). Для уже утверждённого плана 4.2 сначала закрывать самый ранний открытый подпункт [`STAGE4_2_AUTOMATION_PLAN.md`](./STAGE4_2_AUTOMATION_PLAN.md), а не продолжать исторически начатый более поздний.

**Уточнение владельца (2026-11-17):** обоснованный временный пропуск возможен, но **до перехода** исполнитель обязан объяснить владельцу проверяемую причину, независимость следующей работы, риски и условие возврата; записать всё в план и `HANDOFF.md` со статусом `DEFERRED`, не `[x]`. При необходимости дополнительного разрешения — дождаться его. Без доказуемой причины и объяснения перескоки запрещены. Это исключение уточняет предыдущее строгое правило; порядок по умолчанию сохраняется.

**Решение владельца от 2026-11-17 — режим работы без ручной рутины на iPhone:** разработчик самостоятельно обновляет код, запускает офлайн-проверки через GitHub Actions и ведёт этот реестр; владелец получает короткий отчёт по завершённому подпункту. Никаких повторных попыток искать и запускать VS Code Tasks в мобильном Codespaces ради промежуточных проверок. Живые проверки, которым обязательно нужна личная OAuth-сессия, объединяем в одну короткую приёмку после подготовки нескольких функций и только когда это действительно необходимо. **Офлайн-тесты не заменяют живой вызов модели:** GPT native tool-call, refresh, Claude Code и лимиты остаются НЕ проверенными до отдельного подтверждения. Все 11 этапов и исходные критерии остаются без изменений. Платные ресурсы и новые доступы без согласия владельца запрещены.

## 1. Подтверждение жизнеспособности схемы авторизации и затрат

### Контрольный список подпунктов

- [x] **1.1. Проверить актуальные официальные правила OpenAI SIWC/ChatGPT Plus для open-source и self-hosted VM.** **Завершена только документальная проверка (2026-11-16):** OpenAI прямо описывает OSS-приложения на self-hosted VM; OAuth выполняется локально, VM использует отдельный host ID; плановый доступ ограничен условиями и квотами. Через этот маршрут Responses требует `store: false`, `stream: true`, а некоторые hosted-инструменты недоступны. Это **не** проверка фактической авторизации и **не** заключение о соответствии ещё ненаписанного приложения.
- [x] **1.2. Подтвердить применимость правил именно к нашей архитектуре — документальный архитектурный аудит (2026-11-16).** **Условный PASS по опубликованным условиям OpenAI:** реальные рабочие исходники OSS-клиента/движка и оркестрации публикуются, а отдельный экземпляр запускается владельцем на личной self-hosted VM; данные, рабочие проекты, токены и конфигурации остаются приватными. Такой сценарий прямо описан OpenAI. Динамическая регистрация OSS-клиента предусмотрена через `dynamic_agent_client`, без партнёрского API-ключа/секрета; предварительное отдельное одобрение *не указано для этого OSS-пути*. **Граница:** если приложение фактически будет закрытым удалённым SaaS или сервисом для других клиентов, использовать эту оценку нельзя: OpenAI направляет paid/remotely hosted продукты в отдельный interest form. **Не доказано до создания кода:** что наш конкретный клиент соответствует условиям, OAuth разрешит нужные scopes, GPT-модель ответит и будут доступны нужные квоты. Живые проверки остаются подпунктами 1.4–1.7. Не обещать универсальное разрешение OpenAI.

## Общие условия для всех этапов

1. **Не выдавать задуманные функции за уже существующие:** подтверждать реальные тесты, версии и результаты.
2. **Без согласования или ранее выданного гранта не делать:** покупки/платные API (всегда требуют отдельного решения), production вне действующего проектного разрешения, изменение секретов/прав, опасные удаления, сообщения внешним людям и передачу задачи вне правил делегирования владельца.
3. **Защищать исходники:** публичный open-source код платформы отдельно; данные, память, токены, переписки и репозитории проектов — приватны.
4. **Избегать лишних структур:** новые оркестраторы и специализации вводятся только когда дают измеримую пользу.
5. **Текущая работа:** продолжать **этап 1** по уже отмеченным подпунктам и результатам, без повторного выполнения проверенных действий. Для будущих этапов сначала уточнять технические детали и критерии приёмки с владельцем.
